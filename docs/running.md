# Работа со стендом

Первичная установка описана в [первом запуске](quickstart.md).
Все команды ниже выполняются из корня репозитория.

## Запуск, состояние и остановка

| Действие | Windows PowerShell | Linux Bash |
| --- | --- | --- |
| Полный запуск с проверками | `./scripts/start.ps1` | `./scripts/start.sh` |
| Проверка исходников без запуска | `./scripts/check.ps1` | `python scripts/quality/check.py` |
| Состояние контейнеров | `./scripts/compose.ps1 ps` | `./scripts/compose.sh ps` |
| Остановка с сохранением томов | `./scripts/compose.ps1 down` | `./scripts/compose.sh down` |

Обёртки Compose загружают `app/config/lab.env` и `local/secrets/ims.env`.
Вызов `docker compose` без этих параметров не эквивалентен запуску через обёртку.
Проект Compose называется `lab-docker` для совместимости с существующими томами;
это внутренний идентификатор. Его изменение требует переноса томов.
Команда `down -v` удаляет именованные тома, включая базы и кэш моделей;
для обычного перезапуска она не нужна. Файлы `local/` остаются на хосте.

Полный запуск подготавливает SCTP, образы, модели и синтетические аудиосценарии,
настраивает абонентов в OAI UDR и PyHSS, запускает сеть и девять shell-проверок.
Python-проверки переводчика и параллельных звонков выполняются дополнительно.

Для разработки есть `-SkipVerify` в PowerShell или `--skip-verify` в Linux.
Этот режим прогревает модели, но сообщает `STARTED/UNVERIFIED`: звонки не проверены.
`python scripts/start_lab.py --base-only` запускает сеть и IMS без AI и всегда
выполняет три базовые проверки. Сообщение `READY` относится только к выполненному
набору, а не к работе телефона или задержке 1–3 секунды.

Журналы прикладных сервисов:

```powershell
./scripts/compose.ps1 logs -f sip-as voice-agent media-adapter ai-worker
```

## Что запускается

OAI CN5G, эмулированная базовая станция UERANSIM и два абонента с сессиями
`internet` и `ims`; DNS, PyHSS, Kamailio P/I/S-CSCF и RTPengine обеспечивают IMS.
Наши SIP AS, Media Adapter, AI Worker и Voice Agent обрабатывают вызовы и речь.
Whisper распознаёт речь; baseline использует Qwen через Ollama, облегчённые
профили — OPUS-MT внутри AI Worker. Piper синтезирует голос, minimal использует
eSpeak NG. Внутренний формат звука AI — PCMU/8000. Запуск облегчённых вариантов
описан в [quickstart](quickstart.md); при обслуживании сохраняйте `--mode` и
для внешнего OAI также `--partner` в командах `compose_ai.py`.

| Услуга | Параметр номера в lab.env |
| --- | --- |
| Перевод с русского на английский | `VOICE_TRANSLATOR_MSISDN` |
| Запись и расшифровка после звукового уведомления | `VOICE_TRANSCRIBER_MSISDN` |
| Русский участник двустороннего перевода | `VOICE_INTERPRETER_RU_MSISDN` |
| Английский участник двустороннего перевода | `VOICE_INTERPRETER_EN_MSISDN` |

В двустороннем переводе используются два отдельных звонка к сервису:
каждый участник слышит перевод на своём языке, исходный звук напрямую не передаётся.
Обычный разговор абонентов должен продолжаться при отказе AI; вызовы AI-услуг
зависят от соответствующих обработчиков.

Речь собирается в реплики по паузам, затем проходит через ограниченную очередь.
Разные звонки обрабатываются параллельно; состояние одного звонка защищено блокировкой.
Строгий порядок при конкуренции за ресурсы требует отдельной проверки.
У каждого звонка своя очередь озвучки. Речь абонента прерывает ответ ассистента,
но не озвучку перевода. Потоковый режим экспериментальный и по умолчанию выключен.

## Проверки работающего стенда

Запускайте последовательно: проверки используют общий стенд и могут перезапускать
сервисы. Для shell-файлов на Windows используйте Git Bash, например:

```powershell
& 'C:\Program Files\Git\bin\bash.exe' app/tests/integration/verify-ims.sh
```

На Linux: `bash app/tests/integration/verify-ims.sh`.

| Скрипт в app/tests/integration | Что проверяет |
| --- | --- |
| `verify.sh` | Базовая сеть и подключение UE |
| `verify-ims.sh` | IMS-маршруты, DNS и необходимые компоненты |
| `verify-ims-registration.sh` | Регистрация двух SIP-абонентов через IMS |
| `verify-ims-call.sh` | Двусторонний вызов, обработка AS, наблюдение AI и работа RTP при остановке AI |
| `verify-voice-agent.sh` | Вызов голосового сервиса, ACK, RTP и очистка по BYE |
| `verify-real-ai-stream.sh` | Несколько русских реплик и английские голосовые ответы в одном вызове |
| `verify-transcription-recording.sh` | Явно запрошенные запись и расшифровка |
| `verify-bilingual-dialogue.sh` | Четыре реплики двух абонентов, определение языков и нормализация текста |
| `verify-security.sh` | Проверяемые ограничения доступа и приватности |
| `verify_phone_codecs.py` | Синтетический обмен AMR/AMR-WB ↔ PCMU через RTPengine |

Дополнительные проверки:

```powershell
python app/tests/integration/check_bidirectional_interpreter.py
python app/tests/integration/check_parallel_calls.py
python scripts/check-no-hardcoded-topology.py
python app/research/tools/research_run.py verify --root .
```

Обычный вызов считается успешным, когда UE1 получает `200 OK`, UE2 получает
INVITE через IMS, S-CSCF вызывает AS по iFC/ISC, RTPengine видит оба текущих
IMS-адреса, а наблюдение AI связано с Call-ID. При остановке AI счётчики RTP
должны продолжать расти.

Проверка перевода вводит синтетическую русскую речь и требует минимум два
английских голосовых ответа. В отчёте остаются длительности, языки, объёмы текста,
версии обработчиков и задержки, без самих реплик. Проверка параллельности использует
нагрузку `1 → 2 → 1` вызов и отдельные Call-ID; это функциональная проверка,
а не измерение предельной производительности.

Двусторонний перевод измеряет сбор реплики, ожидание очереди, распознавание,
LLM, передачу результата, синтез и отправку RTP. Его результаты не заменяют
измерение момента воспроизведения у слушателя. Сценарий обычного двуязычного
диалога использует [текстовый сценарий](../app/tests/fixtures/bilingual-dialogue-v1.json),
отдельные пороги для длинных исследовательских реплик и требует четыре полные
приватные записи расшифровки. WAV создаются в `local/private/dialogue/`.

Повторная генерация аудиосценариев без запуска всего стенда:

```powershell
./scripts/generate-bilingual-dialogue.ps1
```

## Запись полного эксперимента

```powershell
./scripts/run-interpreter-experiment.ps1
```

Результат — `local/experiments/<UTC-run-id>/`: четыре полных WAV, журналы,
метаданные контейнеров/образов, задержки этапов, контрольные суммы, формат и
длительность аудио, версия Git и итоговый манифест. Принимаемый WAV записывает
PJSUA на стороне абонента, а не сборщик из событий AI. Незакоммиченные изменения
дают `FAIL`, поскольку один хеш коммита не определяет проверенный код.
Полные записи речи остаются приватными. Порядок научных исследований описан
в [research](../app/research/README.md).

## Изолированные проверки Digest и AKA

Следующие команды выполняются на свободном базовом стенде **с остановленными
AS/AI и без активных RTP-сессий**, последовательно. Проверки используют блокировку
стенда, временные профили и восстанавливают обычные клиенты. Проверяйте и основной
результат `status`, и восстановление `cleanup`; неудачные попытки сохраняются.
Перед AKA-проверками соберите [SIPp с поддержкой OPc](sipp-aka-provenance.md).

```powershell
python app/tests/integration/verify_plain_call.py
python app/tests/integration/verify_plain_call.py --caller 2
python app/tests/integration/verify_plain_call.py --mute-ue 1
python app/tests/integration/verify_aka_registration.py
python app/tests/integration/verify_aka_registration.py --bad-response
python app/tests/integration/verify_aka_call.py
python app/tests/integration/verify_aka_call.py --caller 2
python app/tests/integration/verify_aka_lifecycle.py
python app/tests/integration/verify_aka_inactive_call.py --mode deregister
python app/tests/integration/verify_aka_inactive_call.py --mode expire
```

- `verify_plain_call.py` временно отключает AS в iFC. `sip1.log` относится к вызывающему,
  `sip2.log` — к вызываемому, а `receive1.wav` всегда к UE1. Режим `--mute-ue`
  проверяет обнаружение пропавшего источника, поэтому не означает успешную передачу в обе стороны.
- `verify_aka_registration.py` останавливает Digest-клиенты и очищает кэш Contact.
  Используются текущие IMS-маршруты и независимые IMS K/OPc. Отрицательный сценарий
  требует отказа UE1 при корректной регистрации UE2. Отдельно проверяется привязка Cx.
- `verify_aka_call.py` сохраняет один процесс и сокет SIPp от регистрации до конца
  вызова; у REGISTER и INVITE разные Call-ID. RTP-помощник в той же сети UE
  передаёт PCMU по согласованному SDP. Проверяются AKA/Cx, SIP-диалог, маршруты,
  жизненный цикл ретранслятора и звук противоположного источника в каждом WAV.
  Восстановление ограничено `SIP_AKA_RESTORE_TIMEOUT_SECONDS` (90 с), коды ответов
  сохраняются в `restored_clients`. Подробности: [непрерывный AKA-клиент](aka-continuous-client-spike.md).
- `verify_aka_lifecycle.py` выполняет регистрацию, обновление и снятие регистрации
  (`Expires: 0`) одним процессом, со свежим challenge на каждом шаге. Проверяются
  векторы Cx MAA, актуальный Contact, увеличение срока и удаление записи.
  Паузы задают `SIP_AKA_LIFECYCLE_CHECKPOINT_SECONDS` (20 с) и
  `SIP_AKA_LIFECYCLE_FINAL_SECONDS` (5 с). Удаление ограничено
  `SIP_AKA_REGISTRAR_DELETE_TIMEOUT_SECONDS` (210 с): RPC может временно показывать
  уже удаляемую запись. Обычные клиенты до конца наблюдения остановлены.
- `verify_aka_inactive_call.py` сохраняет живой сокет по старому Contact.
  `--callee 1|2` выбирает снимаемого с регистрации абонента. В режиме `expire`
  сначала проверяются неположительный остаток срока, отказ в звонке и отсутствие
  INVITE на старом сокете, затем отдельно — удаление записи. Ожидаются связанный
  с транзакцией `404`, ACK и отсутствие оставшейся RTP-сессии; `408`/`500` не подходят.
  Срок задаёт `SIP_AKA_EXPIRY_SECONDS` (30 с), удержание сокета —
  `SIP_AKA_INACTIVE_HOLD_SECONDS` (600 с), удаление —
  `SIP_AKA_PASSIVE_DELETE_TIMEOUT_SECONDS` (390 с). Cx-захват подтверждает аутентификацию,
  но не последующие LIR/LIA или подтипы SAR незарегистрированного абонента.

Приватные XML с ключами, SIP/PCAP, снимки регистратора, WAV и `result.json`
остаются в `local/private/plain-call-*`, `aka-register-*`, `aka-call-*`,
`aka-lifecycle-*` и `aka-inactive-<mode>-*`. Приём UDP RTP не равен звуку динамика.
Эти проверки не подтверждают весь профиль 3GPP, защиту Gm, повтор nonce,
постоянный UE SQN, синхронизацию AUTS, QoS или задержку перевода.

## Восстановление IMS-сессии и диагностика радиоканала

На свободном базовом стенде с остановленными AS/AI:

```powershell
python app/tests/integration/verify_pdu_recovery.py --ue 1
```

Проверка освобождает настоящую IMS PDU-сессию эмулятора, выбранную по DNN,
и ждёт автоматического восстановления с другим IPv4, новым TUN ifindex,
корректными SIP/RTP-маршрутами, перезапуском SIP-клиента и новым REGISTER 200.
Интернет-сессия и состояние второго UE должны сохраниться. Тот же IP не проходит
проверку смены адреса; восстановление не возвращает принудительно прежний IP.

Перед `nr-cli` проверяется соответствие реестра текущему nr-ue, времени запуска
и принадлежащему ему UDP-сокету. Доказанно устаревшие записи переносятся в
`/tmp/UERANSIM.proc-table-quarantine/` внутри UE; неопределённая принадлежность
даёт отказ. Таймаут задаёт `UE_CLI_TIMEOUT_SECONDS`, отчёты остаются в
`local/private/pdu-recovery-*`.

Новый Contact может сосуществовать со старым. Для проверки его замены нужны
удаление/истечение прежней записи и вызов в рамках того же цикла регистрации.
Позднейший AKA-вызов с перезапуском S-CSCF этого не доказывает. Корреляция PFCP
и физическая мобильность также проверяются отдельно.

Работающий контейнер не гарантирует живую сессию. При `signal lost`, тайм-аутах
`Service Request` или `Discarding RRC Setup Request, UE context already exists`
проверьте журналы UE/gNB и выполните `verify-ims.sh`. На свободном стенде
перезапустите `gnb ue1 ue2` через Compose, затем пересоздайте `sipue1 sipue2`,
чтобы сокеты привязались к текущим IMS-адресам. Повторите регистрацию и неудачную
проверку. Базы и кэш моделей не удаляйте; повторный успех не меняет прежний `FAIL`.

## Настройки, приватность и ограничения

Топология, порты, номера, таймауты, пороги речи и голоса задаются в
[lab.env](../app/config/lab.env). Ключи — только в `local/secrets/ims.env`.
IMS-пул маршрутизируется без NAT; PJSUA находит TUN по подсети, а не номеру интерфейса.
Media Adapter находится в сетевом пространстве RTPengine и наблюдает копию звука.
По Call-ID он запрашивает NG-интерфейс и связывает порт абонента с одной сессией.

Токен внутренних API генерируется в приватном Docker-томе. Voice Agent принимает
звук только от настроенного адреса и пула портов RTPengine. Распознавание и
контекст LLM для перевода обрабатываются в памяти с ограниченным сроком жизни;
аналитика не получает SIP From/To. Ollama доступна только во внутренней сети,
без порта хоста; загрузчик проверяет SHA-256 модели. Образы и зависимости закреплены.

Запись разрешает только вызов `VOICE_TRANSCRIBER_MSISDN` после звукового уведомления.
WAV и текст сохраняются в `local/private/recordings/<идентификатор-сессии>/`.
В baseline LLM исправляет оформление, ошибки распознавания и повторы с требованием сохранять
имена, числа, факты, смысл и порядок реплик. `RECORDING_RETENTION_DAYS` задаёт срок
проверки/удаления; удаление пока выполняет оператор. В обычных журналах остаются
размеры и длительности, не текст реплик.
Облегчённые режимы сохраняют `raw_asr`, без LLM-редактирования текста.

У наших сервисов ограничены ресурсы, журналы и состояние, корневая файловая
система доступна только для чтения; из них только Media Adapter сохраняет `NET_RAW`.
Журналы PyHSS находятся в tmpfs, базы OAI/IMS и модели — в постоянных томах.
Шифрование хранилищ, управление ключами, резервирование и политика удаления
для промышленного развёртывания требуют отдельной настройки.

Это односерверный лабораторный профиль. Репликация AS с привязкой диалога,
постоянное хранение состояния звонка, пул RTPengine, mTLS, KMS/HSM и независимое
масштабирование AI описаны как проект в [обзоре защиты](hardening/hardening.md)
и [предложении архитектуры](hardening/proposals/scalable-private-service-boundary.md).
OmniVoice не входит в основной профиль; его можно оценивать отдельно как GPU TTS.
Статус возможностей: [status.md](status.md); переход к оборудованию:
[physical-5g-stand.md](physical-5g-stand.md).

## Диагностика и перенос

Проверяйте по цепочке: Docker → ядро/PDU → DNS/маршруты → IMS REGISTER → обычный
звонок → AI. Если обычный вызов не работает, смена модели перевода это не исправит.

| Симптом | Что проверить / действие |
| --- | --- |
| Compose не понимает `include`, `!override`, `gw_priority` | Версию Compose и требования [установки](quickstart.md) |
| Нет SCTP или UE не подключается | Журналы AMF/gNB/UE, поддержку SCTP ядром Linux/WSL2; базовый launcher подготавливает SCTP |
| У UE нет IMS PDU | IMS DNN/S-NSSAI в подписке, конфигурации SMF и UE; не путать internet PDU с ims |
| REGISTER без ответа | Адреса DNS/P-CSCF, обратный маршрут к IMS UE, SIP-порт и firewall |
| REGISTER отклоняется | IMPI/IMPU, realm, способ аутентификации и соответствие ключей; журналы Cx; не сбрасывать SQN для обхода ошибки |
| Звонок есть, звука нет/односторонний | SDP, оба маршрута, RTP-диапазон, согласованный кодек; состояние RTPengine |
| AI `unhealthy` | Прогрев, доступность закреплённых Whisper-весов, для OPUS оба manifests, права mount, лимит RAM |
| После смены env ничего не изменилось | Нужен `up -d` с пересозданием, а для build args также `build`; `restart` оставляет старое окружение |
| После перехода на compact снова появился Qwen | Не был ли запущен обычный launcher; использовать явный CPU-профиль во всех командах |
| Контейнер завершён / повторно стартует | `docker stats --no-stream`, `docker inspect --format '{{.State.OOMKilled}}' lab-ai-worker`, журнал контейнера; отдельно проверить лимит ВМ/WSL2 |
| Задержка велика при быстром переводе | Длительность накопления речи, тишина, очередь, STT, TTS и воспроизведение; MT — только один этап |

Для baseline журналы читают обычной Compose-обёрткой, для CPU —
`python scripts/compose_ai.py --mode compact logs --tail 100 <service>`.
Для партнёрского варианта добавляют `--partner` перед `logs`.
Не запускайте full launcher для простого просмотра логов: он меняет стенд.

### Обновление и резервное копирование

1. Зафиксируйте текущий commit, AI-профиль, версии образов, публичную конфигурацию
   и успешные/неудачные проверки. Завершите активные вызовы.
2. Приватно сохраните `local/secrets/ims.env`, локальные OPUS-модели с manifests,
   нужные записи и evidence. Не добавляйте их в исходный архив или Git.
3. Согласованно сохраните именованные тома IMS MySQL, OAI DB (если локальный OAI),
   control token и кэши моделей. Состав томов смотрите в Compose. Для холодной
   копии сначала остановите потребителей и БД; копирование файлов работающей
   MySQL не является согласованной резервной копией. Процедуру restore проверяйте
   на отдельном стенде; универсального автоматического backup/restore здесь нет.
4. Обновите исходники до согласованной версии, соберите изменённые образы,
   примените прежний сценарий запуска и AI-профиль. Не используйте `down -v`.
5. Повторите базовые проверки, обычный вызов и используемые услуги. При откате
   учитывайте совместимость схем БД, не только старый Docker-образ.

Перенос весов не переносит готовый стенд: также нужны образы, зависимости,
секреты, абонентские базы, маршруты и кэш выбранного Whisper. Перед отключением
интернета отдельно проверьте запуск из подготовленных образов и выполнение
реального запроса после прогрева. На другом CPU/архитектуре заново измерьте
ресурсы и проверьте доступность совместимых образов. `minimal` экономит RAM,
но общий образ Voice Agent всё ещё содержит Piper-файлы.
