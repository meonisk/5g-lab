# Услуги IMS ближе к 3GPP: iFC по абоненту, B2BUA, цепочка AS

Статус: дизайн согласован 12.11.2026, реализация не начата. Ветка `partner-ims-ai`.

Это первый из четырёх подпроектов доработки стенда. Остальные идут отдельными
спецификациями: профилирование CPU и задержек, real-time перевод, настоящий телефон.

## Цель

Абонент звонит другому абоненту по обычному номеру, и услуги подключаются так, как
у оператора: по профилю абонента в HSS (iFC), несколькими AS цепочкой через S-CSCF.
Новая услуга добавляется модулем в SIP AS и строкой в профиле абонента, без правок
по всему коду.

Готово, когда:

1. UE1 (`ru`, услуги `translate,record`) звонит UE2 (`en`) по `1002`. Каждый слышит
   перевод речи собеседника на своём языке, исходный голос между ними не проходит,
   у звонка есть расшифровка обеих сторон.
2. Абонент без услуги перевода звонит `*1002`: этот звонок идёт с переводом.
3. Звонок абонента без услуг проходит как обычный.
4. При остановленном `lab-sip-as` звонок соединяется (без услуг).
5. Номера `1003`–`1006` работают как раньше, их проверки проходят без изменений.
6. Сценарии 1–4 проходят на тестовых клиентах SIPUE и через 5G (rfsim UE).

## Сейчас

- У всех абонентов один шаблон iFC (`vendor/docker_open5gs/pyhss/default_ifc.xml`,
  приоритет 30): исходящий `INVITE` → `sip:as.<IMS_DOMAIN>:SIP_AS_PORT`.
- SIP AS (`app/services/sip-as/ims_sip/`, ~500 строк) — прокси. По номеру
  (`service_mode_for_request`) он сам отвечает на `1003`–`1006`, остальные вызовы
  возвращает в S-CSCF и наблюдает за ними (`observe`).
- Двусторонний перевод — две независимые ноги к агенту (`1005`, `1006`); AI Worker
  ищет единственную ногу противоположного языка (`interpretation.delivery_call`),
  поэтому на стенде возможна только одна пара переводчиков.
- S-CSCF (Kamailio) использует `ims_isc`: `isc_match_filter` и `isc_from_as`, то есть
  механизм цепочки iFC уже есть.

## Решение (подход A)

Один контейнер `lab-sip-as`, внутри — логические AS: у каждой услуги свой SIP URI и
свой модуль. Для S-CSCF это разные AS; физически — один процесс (меньше CPU и памяти
на сервере, который делит CPU с rfsim). Позже модуль можно вынести в свой контейнер
без изменения снаружи.

Отклонены: контейнер на услугу (те же свойства снаружи, больше ресурсов);
FreeSWITCH/Asterisk как AS + MRF (смена платформы и переписывание AI-стека).

## Архитектура

### Сигнализация

Звонок UE1 → UE2, у UE1 в профиле `translate,record`:

1. UE1 → P-CSCF → S-CSCF (originating). S-CSCF применяет iFC UE1 по приоритетам.
2. Приоритет 10 → `sip:translate.as.<IMS_DOMAIN>`. Translate AS — B2BUA: принимает
   ногу A от UE1, создаёт ногу B и отправляет её в S-CSCF, который продолжает цепочку
   со следующего приоритета.
3. Приоритет 20 → `sip:record.as.<IMS_DOMAIN>`. Record AS — прокси: помечает звонок
   для записи и возвращает запрос в S-CSCF.
4. S-CSCF → I-CSCF / S-CSCF вызываемого → UE2.

Имена `translate.as` и `record.as` добавляются в DNS (`lab-dns`) и указывают на
адрес SIP AS. SIP AS различает услугу по Route/Request-URI, которые ставит S-CSCF.

### Профиль абонента

В `lab.env`:

```text
UE1_SERVICES=translate,record
UE1_LANGUAGE=ru
UE2_SERVICES=
UE2_LANGUAGE=en
DEFAULT_LANGUAGE=ru
```

`provision.py` собирает XML iFC для каждого абонента (вместо общего
`default_ifc.xml`) из таблицы услуг: URI, приоритет, триггер, `DefaultHandling`.
Каждому абоненту дополнительно добавляется правило «Request-URI начинается с `*`» →
translate AS: так префикс `*номер` разово включает перевод. Translate AS отрезает `*`
и ведёт звонок на номер без префикса. Существующее правило для `1003`–`1006` и
`observe` сохраняется (услуга `numbers`, наименьший приоритет).

Обслуживаемого абонента AS узнаёт из заголовка `P-Served-User` (S-CSCF его уже
добавляет: `add_p_served_user=1`), язык — по таблице `MSISDN → язык`, которую SIP AS
читает из `lab.env` при старте. Язык вызываемого — по той же таблице по номеру в
Request-URI.

Нога B проходит и правило `numbers` (приоритет 30): для неё это обычный звонок, режим
`observe`. Чтобы не распознавать ногу B дважды, `numbers` пропускает диалоги, которые
создал сам SIP AS.

### SIP AS: код

```text
app/services/sip-as/ims_sip/
  core/      SIP-транспорт, диалоги, B2BUA (две ноги), SDP, клиент MRF
  services/
    translate.py   B2BUA с переводом
    record.py      прокси с пометкой записи
    numbers.py     нынешние 1003–1006 и observe, поведение не меняется
```

Модуль услуги объявляет свой URI и реализует обработчики `on_invite`, `on_answer`,
`on_bye`. Всё остальное (транзакции, Via, Route, ответы, освобождение MRF) делает
`core`.

### Медиа (MRF)

Media Adapter и Voice Agent остаются отдельными сервисами, но управляются через одно
явное API MRF в `core`: «привязать ногу», «играть в ногу», «отдавать поток на
распознавание», «освободить».

Переводимый звонок:

- нога A (UE1 ↔ MRF): AS отвечает UE1 с SDP на порт Voice Agent — как сейчас при
  звонке на `1005`;
- нога B (MRF ↔ UE2): AS отправляет `INVITE` к UE2 через S-CSCF с SDP на второй порт
  Voice Agent — как будто UE2 позвонил на `1006`;
- AS держит ногу A в `180 Ringing` и отвечает UE1 `200 OK` только после `200 OK` от UE2;
- AS сообщает AI Worker пару: «ноги A и B, языки ru и en». Это заменяет поиск
  единственной противоположной ноги в `delivery_call` и снимает ограничение «одна
  пара переводчиков на стенд»;
- если языки сторон совпадают, translate AS не вмешивается и работает как прокси.

Запись:

- record AS помечает звонок по Call-ID;
- если в звонке есть перевод, AI Worker уже распознаёт обе ноги и сохраняет тексты
  обеих сторон;
- без перевода Media Adapter получает звук из RTPengine (как в `observe`), AI Worker
  пишет расшифровку;
- перед записью каждой стороне проигрывается уведомление, как на `1004`; формат
  каталога записи — тот же, что у `1004`.

## Ошибки

| Ситуация | Поведение |
|---|---|
| SIP AS недоступен | `DefaultHandling` = `SESSION_CONTINUED` для обеих услуг: звонок идёт без услуги |
| нет свободного MRF (`VOICE_AGENT_MAX_CALLS`; переводимый звонок занимает 2 места) | translate AS пропускает звонок без перевода и пишет это в лог; `503` звонящему не отдаётся |
| UE2 отвечает `486` / `480` / `408` | AS передаёт тот же ответ UE1, освобождает MRF |
| `BYE` или `CANCEL` с любой стороны | AS отправляет `BYE` / `CANCEL` другой ноге, освобождает MRF и пару в AI Worker |
| re-INVITE / UPDATE (удержание, session timer) | AS отвечает на своей ноге прежним SDP на MRF и не пересылает запрос на другую ногу |
| язык абонента не задан | `DEFAULT_LANGUAGE` |

## Риск, проверяемый первым

Вторая нога от B2BUA должна вернуться в S-CSCF так, чтобы `ims_isc` продолжил
цепочку iFC со следующего приоритета, а не начал заново и не пропустил record AS.
Первый шаг реализации — spike: два пустых логических AS в цепочке, звонок SIPUE1 →
SIPUE2 проходит через оба по порядку (видно в логах SIP AS и S-CSCF). Если не
проходит — сначала правится конфиг S-CSCF, потом пишутся услуги.

## Проверки

Unit (без Docker):

- генерация iFC из `lab.env`: приоритеты, правило `*`, `DefaultHandling`, абонент без
  услуг;
- модули на фейковом SIP: создание ноги B, `180` до ответа UE2, `486`, `BYE` с каждой
  стороны, `CANCEL`, re-INVITE, одинаковые языки, нет MRF.

Интеграционные:

- `app/tests/integration/verify-services.sh` на SIPUE — сценарии 1–4 из «Готово,
  когда»: перевод в обе стороны, исходный голос не проходит (в ноге B нет речи UE1),
  расшифровка обеих сторон, `*номер`, звонок без услуг, остановленный `lab-sip-as`;
- те же сценарии в `verify-5g-ue.sh` через rfsim UE;
- регрессия: `verify-ims.sh`, `verify_interpreter.py` и проверки `1003`/`1004` без
  изменений.

## Не входит

- MMTel (переадресация, ожидание, запрет вызова);
- управление услугами с телефона (Sh, XCAP/Ut);
- конференции на 3 и более участников;
- профилирование, real-time перевод, настоящий телефон — отдельные подпроекты.
