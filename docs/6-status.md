# 6. Итоги: что работает, соответствие 3GPP, замеры

Состояние на 13.11.2026, ветка `partner-ims-ai`. Подробности по каждой теме — в
документах 1–5, здесь — сводка.

## Что умеет стенд

- Звонки между абонентами через IMS поверх ядра 5G OAI CN5G.
- Услуги по профилю абонента (iFC в HSS) и по номерам: перевод разговора между
  абонентами ru ↔ en, разовый перевод `*номер`, запись обеих сторон, расшифровка,
  голосовой переводчик, SMS. Как это устроено — [документ 2](2-architecture.md).
- Распознавание (Whisper), перевод (OPUS-MT) и синтез (Piper) работают локально на CPU,
  без облака.
- Проверки: `verify-all.sh`, звонки через 5G — `verify-5g.sh`, замеры —
  `profile.sh`, длинный разговор — `conversation.py` ([документ 3](3-5g-and-profiling.md)).

## Путь звонка и соответствие 3GPP

Полный путь проверяет `python3 scripts/profile/conversation.py --5g`: UE1 звонит UE2,
оба говорят, перевод идёт в обе стороны.

```text
UE1 (PJSUA) → gNB rfsim → UPF → P-CSCF → S-CSCF → AS translate → AS record → S-CSCF → P-CSCF → UPF → gNB rfsim → UE2
                                 звук: UE ↔ UPF ↔ rtpengine ↔ Media Adapter → AI Worker → Voice Agent → rtpengine
```

Как в 3GPP:

| Участок | Что работает |
|---|---|
| Радио | OAI gNB и nr-UE, настоящий стек NR (RRC, PDCP, RLC, MAC, NAS); эмулируется только эфир — RF Simulator вместо антенны |
| Ядро 5G | регистрация UE в AMF по 5G-AKA, PDU-сессия в SMF на DNN IMS, звук и SIP через UPF (GTP-U, N3 → N6) |
| Адрес P-CSCF | выдаёт SMF при подключении (`ims.pcscf_ipv4`); S-CSCF видит адрес UE из туннеля, а не адрес UPF |
| IMS | P-CSCF → I-CSCF → S-CSCF (Kamailio), HSS (PyHSS) по Diameter Cx |
| Услуги | iFC по абоненту из HSS, сервер услуг по ISC как B2BUA, цепочка из нескольких услуг |
| Звук | rtpengine — медиашлюз; AI получает и возвращает звук в RTP того же звонка |

Упрощено:

| Что | Как здесь | Как у оператора | Когда важно |
|---|---|---|---|
| Вход в IMS | SIP Digest (MD5), пароль — ключ абонента в PyHSS: PJSUA не умеет AKA | IMS-AKA по ключу SIM | настоящий телефон |
| Защита SIP | без IPsec, UDP открыто (поддержка в P-CSCF есть, клиент её не использует) | IPsec между телефоном и P-CSCF | настоящий телефон |
| QoS голоса | общий поток PDU-сессии IMS; Rx выключен — у PCF ядра нет Diameter | отдельный поток 5QI=1 через PCF (N5/Rx) | нагрузка на радио |
| Кодек | PCMU 8 кГц | AMR-WB обязателен, EVS рекомендован | настоящий телефон; AMR → PCMU умеет rtpengine, EVS не проверен |
| Медиаресурс | Voice Agent и rtpengine | MRF (MRFC/MRFP) | — |

## Замеры

Сервер kopatych: 8 логических ядер (4 физических), режим `compact` (Whisper base, 2
потока; OPUS-MT; Piper). Цель — перевод не позже 2 с после конца фразы при работающем
rfsim.

### Одна фраза на переводчик 1003 (`profile.sh`, S3/S4)

| Сценарий | От конца речи до перевода | Распознавание |
|---|---|---|
| S3: сеть ядра, без rfsim | 1834–2233 мс | 1022–1139 мс |
| S4: 5G, rfsim, без привязки к ядрам | 2589–3169 мс | 1697–1810 мс |
| S4: AI Worker на одном физическом ядре (`3,7`) | 3632–4102 мс | 2630–2715 мс |
| S4: AI Worker `2,3,6,7`, rfsim `0,1,4,5` | **2176–2235 мс** | 1223–1344 мс |

Привязка к ядрам (`AI_WORKER_CPUSET`, `RFSIM_CPUSET`) — главный выигрыш под rfsim: AI
Worker и rfsim не делят физические ядра. Одно физическое ядро хуже, чем без привязки.
Значения зависят от компьютера, в git они пустые ([документ 3](3-5g-and-profiling.md)).

### Длинный разговор через 5G (`conversation.py --5g`)

96 с, 20 предложений, оба собеседника говорят в обычном темпе и не ждут перевода.
Привязка `2,3,6,7` / `0,1,4,5`.

| | ru→en | en→ru |
|---|---|---|
| фразы | 12, все по границе предложения | 8 |
| переведено / озвучено / прервано | 12 / 12 / 0 | 8 / 8 / 0 |
| точность распознавания | 81% | 98% |
| задержка, медиана / макс | 3,4 / 5,3 с | 3,0 / 5,0 с |
| пауза / распознавание / перевод / синтез, медианы | 353 / 1778 / 252 / 752 мс | 391 / 1565 / 177 / 606 мс |

Каждый перевод синтезируется заново (в кэше Voice Agent только приветствия и
уведомления). Остаток ~250 мс сверх суммы этапов — передача текста в Voice Agent и
начало RTP. Прошлый прогон с кэшем озвучек показал 2,9 / 2,25 с — en→ru тогда
выглядел быстрее, чем есть. Для сравнения, тот же разговор локально (12 ядер, без
rfsim): медиана 1,6 с, этапы 330 / 750 / 90 / 360 мс.

Сервер медленнее рабочего компьютера в ~1,5 раза уже без нагрузки (S3), rfsim добавляет
ещё ~1,3 раза. Радиопуть почти не добавляет задержки: разговор по сети ядра под
нагрузкой rfsim — 3,0 / 2,9 с. Время уходит на обработку: больше половины —
распознавание, затем синтез.

## Что сделано для задержки

| Изменение | Эффект |
|---|---|
| Фраза закрывается на паузе 250 мс, если она длиннее 2,5 с; на 10 с режется по самой длинной паузе | одна фраза = одно предложение; задержка 2,6 → 1,7 с, максимум 11,5 → 4,3 с (локально) |
| Voice Agent синтезирует следующий перевод, пока звучит текущий; ожидающий перевод на 15% быстрее | очередь не растёт к концу реплики; медиана 1,6 с (локально) |
| Привязка AI Worker и rfsim к разным физическим ядрам | S4 2,6 → 2,2 с |
| Отдельный лимит переводов для переводчика (`AI_INTERPRETER_MAX_REPLIES_PER_CALL`) | длинный разговор переводится целиком, а не 4 фразы |

Не помогло (проверено замером): опции Whisper `vad_filter` и `without_timestamps`;
короче окно Whisper (`chunk_length` 8–15 с) — faster-whisper всё равно дополняет вход
до 30 с; приоритет `cpu-shares`. Whisper `tiny` быстрее на 35%, но теряет 13 п.п.
точности.
