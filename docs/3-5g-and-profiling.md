# 3. Проверка через 5G и замеры

Тестовые телефоны `lab-sipue1/2` подключены прямо к сети ядра и 5G не проходят.
Путь настоящего телефона (радио → gNB → ядро → UPF → IMS) проверяется эмулятором
радио OAI RF Simulator (rfsim): на одном компьютере работают базовая станция (gNB) и
два эмулированных телефона (UE1, UE2). Внутри каждого эмулированного телефона
запускается тот же SIP-клиент PJSUA.

Нужно: собранный OAI RAN на этом компьютере и `sudo`. Пути по умолчанию —
`~/openairinterface5g` (`OAI_RAN_DIR`) и `~/projects/oai_configs` (`OAI_RAN_CONF_DIR`).

## Проверка звонков через 5G

```bash
scripts/verify-5g.sh
```

Поднимает радио, проверяет звонки и останавливает радио, даже если проверка упала.
Занимает 4–5 минут. Проверки:

| Тест | Что проверяется |
|---|---|
| сессии | у каждого UE есть адрес из `IMS_UE_CIDR`, P-CSCF доступен через туннель 5G |
| регистрация | S-CSCF видит адрес UE из туннеля, а не адрес UPF |
| A | UE1 → 1003: приветствие и перевод |
| B | UE2 → UE1: обычный звонок, звук в обе стороны |
| C | UE2 → 1004: фраза распознана |
| D | UE1 → UE2: перевод ru → en и запись обеих сторон |
| E | UE2 → `*UE1`: разовый перевод en → ru |
| F | сервер услуг остановлен: UE1 → UE2 всё равно соединяется |

Итог: `5G UE -> IMS -> AI: PASS`. Радио можно поднимать и проверять отдельно:

```bash
scripts/rfsim.sh up        # gNB и два UE
scripts/rfsim.sh status    # процессы и адреса
bash app/tests/integration/verify-5g-ue.sh
scripts/rfsim.sh down
```

`rfsim.sh up` отказывается стартовать, если уже работает другой gNB или UE. Остался
прошлый запуск — `scripts/rfsim.sh down`. Журналы: `local/rfsim/gnb.log`,
`ue1.log`, `ue2.log`, `pjsua-ue1.log`, `pjsua-ue2.log`. Если после прерванного
прогона терминал печатает «лесенкой» или не видно ввода — `stty sane`.

## Замер задержки и нагрузки

Цель проекта — перевод не позже 2 с после конца фразы при работающем rfsim на том же
процессоре.

```bash
scripts/profile.sh --quick     # примерно 10 минут
scripts/profile.sh             # полный перебор, около часа
```

Стенд должен быть запущен. Скрипт сам поднимает и останавливает rfsim и в конце
возвращает стенд в исходное состояние. Результат — в `local/profile/<время>/`:
`report.md` (читать), `report.json` (то же для программ), `profile.log` (журнал).

Что измеряется:

| Часть | Что делает |
|---|---|
| S1 | стенд без звонков: сколько процессора занято в простое |
| S2 | то же с работающим rfsim |
| S3 | тестовый телефон из сети ядра звонит на 1003, без rfsim |
| S4 | UE1 через 5G звонит на 1003, с rfsim |
| S5 | одновременно два звонка с переводом при работающем rfsim |
| перебор | без звонка: модели Whisper tiny/base/small и число потоков распознавания на тех же фразах; время и точность |

Фразы для замеров озвучивает Piper. Голос тестовых клиентов espeak-ng Whisper
распознаёт плохо: замер на нём показывает мусорный текст и завышенное время.
Недостающие модели Whisper скрипт скачивает перед перебором.

### Как читать отчёт

- **CPU по сценариям** — занятые ядра процессора (1.0 = одно ядро полностью), среднее
  и 95-й процентиль. Сравнивайте S1 с S2 (сколько стоит rfsim) и S3 с S4 (звонок под
  нагрузкой). Если `lab-ai-worker` упирается в свой лимит `AI_WORKER_CPU_LIMIT`, его
  тормозит лимит контейнера, а не весь компьютер.
- **Задержка по этапам** — медиана по раундам:

  | Этап | Что это |
  |---|---|
  | ожидание паузы | сколько тишины ждём, чтобы понять, что фраза кончилась (`AI_UTTERANCE_SILENCE_MS`, 700 мс) |
  | очередь | ожидание свободного обработчика |
  | распознавание | Whisper |
  | перевод | OPUS-MT или Qwen |
  | синтез | Piper |
  | итог | от конца речи до первого звука перевода |

- **Перебор** — точность = 1 − WER (доля неверно распознанных слов). Числа словами и
  цифрами считаются разными словами, поэтому сравнивайте варианты между собой, а не с
  100%.
- **Итог** — самый долгий этап и до трёх вариантов настроек, которые укладываются в
  2000 мс без потери точности больше 10 процентных пунктов относительно `compact`.
  Оценка варианта = пауза + распознавание и перевод из перебора + синтез из звонка.

### Текущие результаты (режим `compact`, сервер kopatych, 8 ядер, 13.11.2026)

| Сценарий | От конца речи до перевода | Распознавание |
|---|---|---|
| S3, без rfsim | 1834–2233 мс (медиана 1929) | 1022–1139 мс |
| S4, с rfsim, через 5G, без привязки к ядрам | 2513–3169 мс (медиана ~2670) | 1559–1836 мс |
| S4, с rfsim, AI Worker на `2,3,6,7`, rfsim на `0,1,4,5` | 2176–2235 мс (медиана 2196) | 1223–1344 мс |

Главный этап — распознавание. Без привязки к ядрам rfsim замедляет Whisper base в
1,6 раза; с привязкой (раздел «Привязка к ядрам при rfsim») — в 1,2 раза, и до цели 2 с
остаётся ~200 мс. Лишние потоки не помогают: 2 потока на лимите 2 ядра быстрее, чем 4.

S5 в `compact` пропускается: Voice Agent обслуживает не больше двух звонков на
услуги (`VOICE_AGENT_MAX_CALLS=2`), а перевод между абонентами уже занимает оба места.

## Длинный разговор в обычном темпе

```bash
python3 scripts/profile/conversation.py     # около 3 минут, стенд запущен, rfsim не нужен
```

SIPUE1 (русский) звонит SIPUE2 (английский) через услуги translate и record. Разговор —
6 реплик, 20 предложений, 96 с (`app/tests/fixtures/conversation-long-v1.json`, голос
Piper). Паузы как у живого человека: 350 мс между предложениями, ответ через 1,5 с после
конца чужой реплики. Собеседники не ждут, пока дозвучит перевод.

Результат — в `local/conversation/<время>/`:

- `report.md` — по каждому направлению: на сколько фраз AI разделил речь и почему
  (`silence` — обычная пауза 600 мс; `short-pause` — фраза длиннее 2,5 с и пауза
  250 мс, обычно граница предложения; `pause-cut` — фраза дошла до 10 с и разрезана по
  самой длинной паузе внутри неё; `maximum-duration` — разрезана посреди звука),
  сколько фраз переведено, сколько озвучено полностью и сколько прервано, точность
  распознавания, задержка по фразам и её рост к концу разговора;
- `conversation.log` — все события по времени от начала разговора: когда сказано
  предложение, когда сервер закрыл фразу и какие слова в неё попали, что распознано,
  перевод, когда перевод зазвучал и сколько звучал. Время слов внутри предложения —
  оценка по числу букв.

Тексты берутся из записи звонка (`timeline.jsonl` рядом с `transcript.txt`) и остаются
в `local/`. Итог FAIL — если какая-то фраза не переведена, озвучка прервана или точность
ниже 70%.

Результаты на рабочем компьютере (`compact`, 12 ядер):

| | Фразы | Точность ru / en | Задержка, медиана / макс |
|---|---|---|---|
| конец фразы только по паузе 600 мс | склеены до 10 с, режутся посреди слова | 80% / 96% | 2,6 / 11,5 с |
| плюс короткая пауза 250 мс | одна фраза = одно предложение, 4–6 с | 88% / 99% | 1,7 / 4,3 с |

Оставшиеся задержки 3–4 с — в конце длинной реплики: перевод звучит чуть дольше
исходной речи, и следующий перевод ждёт, пока доиграет предыдущий. Чтобы очередь не
росла, Voice Agent синтезирует следующий перевод, пока звучит текущий, и делает его на
15% быстрее (`VOICE_AGENT_CATCHUP_LENGTH_FACTOR`; в журнале — «ускорен ×0.85»).
С этим медиана — 1,6 с.

Из чего складываются 1,6 с одной фразы (рабочий компьютер): ожидание паузы 250–600 мс,
распознавание ~700 мс, перевод ~100 мс, синтез ~300 мс (ffmpeg ~50 мс), отправка RTP.
Опции Whisper (`vad_filter`, `without_timestamps`) не ускоряют: время занимает
кодировщик, он всегда обрабатывает 30-секундное окно. Whisper `tiny` быстрее на 35%,
но теряет 13 п.п. точности.

### Привязка к ядрам при rfsim

Распознавание замедляется под rfsim не из-за нехватки процессорного времени, а из-за
соседей на тех же физических ядрах (общий кэш, гиперпоточность). Замер на 12
логических ядрах (6 физических), все остальные ядра заняты:

| Условия | Распознавание |
|---|---|
| без нагрузки | 708 мс |
| нагрузка, без привязки | 1028 мс |
| нагрузка, приоритет `cpu-shares` ×8 | 1004 мс |
| нагрузка, AI Worker на двух своих физических ядрах | 798 мс |

Сервер kopatych (8 логических ядер = 4 физических, пары `n` и `n+4`), S4 с rfsim:

| AI Worker / rfsim | Распознавание | От конца речи до перевода |
|---|---|---|
| без привязки | 1697–1810 мс | 2589–3169 мс |
| `3,7` / `0-2,4-6` (AI Worker — одно физическое ядро) | 2630–2715 мс | 3632–4102 мс |
| `2,3,6,7` / `0,1,4,5` (по два физических ядра) | 1223–1344 мс | 2176–2235 мс |

Одно физическое ядро (две половины гиперпоточности) хуже, чем вовсе без привязки:
Whisper работает в два потока, и они делят одно ядро.

Как настроить: `lscpu -e` показывает столбец CORE — логические ядра с одним номером CORE
делят одно физическое. Отдайте AI Worker два физических ядра целиком, rfsim — остальные:

```text
AI_WORKER_CPUSET=2,3,6,7  # kopatych: CORE 2 и 3 целиком
RFSIM_CPUSET=0,1,4,5      # CORE 0 и 1
```

В `lab.env` в git оба значения пустые: номера ядер зависят от компьютера, а несуществующее
ядро не даёт запустить контейнер. На сервере правьте `lab.env` локально.

Затем `python3 scripts/start.py` и `scripts/profile.sh --quick`; сравните S4 до и после.
gNB rfsim чувствителен к нехватке процессора: если в его журнале растут ошибки (`CCE
fail`, обрывы UE), ядер для rfsim мало.

Бенчмарк сети и SIP через 5G — `python3 scripts/bench_5g.py --rounds 3`: время
REGISTER и INVITE, задержка пакетов через 5G и напрямую, этапы перевода. Отчёт — в
`local/bench/`.
