# Туториал 1. IMS рядом с ядром OAI

Ядро 5G (OAI CN5G), радиосеть и SIM-карты уже работают у вас. Рядом с ядром, на
том же Docker-хосте, запускаются наши IMS (DNS, PyHSS, P/I/S-CSCF, RTPengine) и
AI-услуги (SIP AS, Media Adapter, AI Worker, Voice Agent, LLM). Все они подключаются
к Docker-сети ядра со статическими адресами.

Три туториала — одна последовательность на одном стенде:

1. **Этот туториал** — подключаем IMS к ядру, регистрируем телефоны, звоним 1001 → 1002.
2. [Туториал 2](guide-2-ims-ai.md) — добавляем AI к уже работающей IMS, не
   перезапуская её, и проверяем услуги 1003–1006.
3. [Туториал 3](guide-3-sip.md) — разбираем SIP-серверы и клиентов на том же стенде;
   в конце — остановка.

Стенд между туториалами не останавливайте: каждый следующий продолжает предыдущий.
Команды выполняются из корня репозитория.

# Часть 1. Команды

**1. Что нужно.** Linux x86-64, Docker Engine 28+ с Compose 2.33+, `git`, `curl`,
`python3` 3.11+ (только стандартная библиотека). Ядро OAI уже запущено в Docker на
этом же хосте. При первом запуске нужен интернет: образы, Whisper, Qwen около 2,5 ГБ.

**2. Изменения в ядре OAI.** В конфигурации SMF и UPF (подробно — [раздел 4](#4-что-меняется-в-ядре-oai)):

```yaml
dnns:
  - dnn: "ims"
    pdu_session_type: "IPV4"
    ipv4_subnet: "12.1.1.0/24"      # = IMS_UE_CIDR в lab.env
smf:
  ue_dns:
    primary_ipv4: "192.168.70.160"  # = DNS_IP
  ims:
    pcscf_ipv4: "192.168.70.166"    # = PCSCF_IP
upf:
  support_features:
    enable_snat: no                 # NAT включаем вручную, только в интернет
```

На UPF (в контейнере UPF или в его entrypoint) интернет-трафик UE по-прежнему
проходит через NAT, а трафик к IMS идёт без NAT:

```bash
iptables -t nat -A POSTROUTING -s 12.1.1.0/24 ! -d 192.168.70.128/26 -j MASQUERADE
```

У абонентов в UDR должен быть разрешён DNN `ims`. После изменений перезапустите SMF и UPF.

**3. Исходники**

```bash
git clone https://github.com/meonisk/5g-lab.git
cd 5g-lab
```

**4. Настройки.** Откройте [app/config/lab.env](../app/config/lab.env) и сверьте:

```bash
docker network ls                                   # имя сети ядра -> CORE_NETWORK_NAME
docker network inspect oai-cn5g --format '{{json .IPAM.Config}}'   # -> LAB_NETWORK_CIDR
docker network inspect oai-cn5g --format '{{range .Containers}}{{.Name}} {{.IPv4Address}}{{"\n"}}{{end}}'
```

В `lab.env` проверьте `CORE_NETWORK_NAME`, `LAB_NETWORK_CIDR`, `UPF_IP`,
`IMS_UE_CIDR`, `INTERNET_UE_CIDR`, адреса `*_IP` (должны быть свободны в сети ядра),
а также IMSI, MSISDN и ключи телефонов `UE1_*`, `UE2_*` (как на SIM и в UDR).

**5. Проверка конфигурации**

```bash
python3 scripts/start.py --check
```

Результат: `CONFIG: VALID`. Скрипт сверяет `lab.env` с реальной сетью ядра: подсеть,
свободные адреса, пулы UE вне подсети.

**6. Запуск IMS**

```bash
python3 scripts/start.py --ims-only
docker compose --env-file app/config/lab.env ps
```

Результат: `STARTED: IMS` и ровно семь контейнеров `Up`: `lab-dns`, `lab-mysql`,
`lab-pyhss`, `lab-icscf`, `lab-scscf`, `lab-rtpengine`, `lab-pcscf`. AI-контейнеров
ещё нет — их добавит туториал 2.

**7. Проверка регистрации**

```bash
bash app/tests/integration/verify-ims.sh
```

Результат: `IMS DNS + HSS + REGISTRATION: PASS`. Тест на время проверки поднимает два
тестовых SIP-клиента `lab-sipue1/2` прямо в сети ядра, регистрирует их и в конце
удаляет: после теста в `docker compose ps` снова семь контейнеров.

**8. Телефоны.** Включите на телефонах 5G и VoNR: в `docker logs --tail 100 lab-scscf`
появятся `REGISTER`, `401`, `200`. Позвоните с 1001 на 1002. SIP AS ещё не запущен,
поэтому S-CSCF после неудачной попытки вызвать его продолжает вызов сам (правило iFC
`DefaultHandling 0`); соединение может занять на несколько секунд дольше. Если что-то
не так — [проверка по шагам](#6-проверка-по-шагам-вызова).

Стенд не останавливайте: дальше — [туториал 2](guide-2-ims-ai.md), он добавит AI к
этой же IMS.

# Часть 2. Как устроено

## 1. Что запускается

Всё описано в одном [docker-compose.yml](../docker-compose.yml). Он подключает два
фрагмента: [ims.yml](../app/infrastructure/compose/ims.yml) с сервисами IMS и
тестовыми клиентами и [ai.yml](../app/infrastructure/compose/ai.yml) с AI-услугами.
Сеть ядра объявлена как `external`. Её создаёт и удаляет ядро, наш Compose только
подключает к ней контейнеры. Схема с контейнерами, адресами и сетями — в
[туториале 2](guide-2-ims-ai.md#1-схема); ниже на неё ссылаются номера шагов.

Все параметры лежат в одном файле [app/config/lab.env](../app/config/lab.env): адреса,
номера, ключи SIM, модели, лимиты. Ключи лабораторные, поэтому хранятся вместе с
остальными настройками. Если в файле стоят ключи настоящих SIM, не публикуйте его.
Compose читает файл через `--env-file`, поэтому любая команда `docker compose`
для стенда начинается с `docker compose --env-file app/config/lab.env`.

## 2. Три уровня одного вызова

Звонок через IMS проходит три независимых уровня. В этом туториале работают первые
два; третий, AI, добавляет туториал 2. За каждый отвечают свои
компоненты, и каждый уровень почти ничего не знает о соседнем. Это помогает искать
неисправность: сначала определяют уровень, потом ищут причину внутри него.

**Транспорт — ядро 5G.** Ядро OAI доставляет IP-пакеты телефона, но не понимает,
что внутри SIP или голос. Телефон получает PDU-сессию в DNN `ims` с адресом из пула
`IMS_UE_CIDR`, а вместе с ней адреса DNS и P-CSCF (SMF передаёт их в PCO). Пакеты
телефона идут по радио на gNB, оттуда в туннеле GTP-U (N3) на UPF. UPF извлекает их
из туннеля и выпускает в Docker-сеть ядра. Обратно наши контейнеры отправляют пакеты
на адрес телефона через UPF: у каждого контейнера IMS есть маршрут
`IMS_UE_CIDR via UPF_IP`. За этот уровень отвечает владелец ядра. Ему достаточно
трёх вещей: DNN `ims`, адресов DNS/P-CSCF в SMF и обмена пакетами между UPF и
нашими адресами без NAT.

**Сигнализация — IMS.** Поверх IP телефон говорит с нашими серверами по SIP:
регистрируется (`REGISTER`), звонит (`INVITE`), кладёт трубку (`BYE`). P-CSCF —
единственная точка входа для телефона. I-CSCF при регистрации выбирает S-CSCF.
S-CSCF хранит регистрацию, проверяет ключи и решает, куда направить вызов. Все трое
обращаются к HSS (PyHSS) по Diameter Cx. В HSS хранятся абоненты, их IMS-ключи и
правила iFC, которые отправляют вызов в наш SIP AS. Ядро видит этот уровень только
как UDP на порт 5060 адреса P-CSCF.

**Медиа и AI.** Голос идёт отдельно от SIP: это RTP-пакеты между телефоном и
RTPengine. P-CSCF при каждом вызове заменяет в SDP адрес телефона на адрес RTPengine,
поэтому весь звук проходит через него. Обычный разговор RTPengine пересылает
собеседнику. Вызов на номер услуги он соединяет с Voice Agent, а Media Adapter
забирает копию звука для AI Worker. Ядро видит этот уровень как UDP на порты
30000–30100 RTPengine.

## 3. Один вызов от начала до конца

Пройдём один вызов на 1003 (перевод с русского на английский) с момента включения
телефона. Шаги 1–7 работают уже после этого туториала, шаги 8–12 — после туториала 2. Номера шагов совпадают с цифрами на стрелках [схемы](guide-2-ims-ai.md#1-схема).
Адреса указаны для значений по умолчанию из `lab.env`.

**Шаг 1. PDU-сессия IMS.** Телефон регистрируется в 5G (AMF, AUSF и UDM ядра
проверяют 5G-ключи SIM) и открывает PDU-сессию в DNN `ims`. SMF выделяет адрес из
пула, например `12.1.1.5`, и передаёт адреса DNS `192.168.70.160` и P-CSCF
`192.168.70.166`. С этого момента любой пакет телефона к нашим адресам идёт по радио
на gNB, затем в GTP-U туннеле на UPF `192.168.70.134`.

**Шаг 2. REGISTER на P-CSCF.** Телефон отправляет `REGISTER` на `lab-pcscf:5060`
(UDP). UPF извлекает пакет из туннеля и выпускает его в сеть `oai-cn5g` без NAT:
P-CSCF видит настоящий адрес `12.1.1.5`. Этот адрес записан и в самом SIP-сообщении
(Via, Contact), поэтому NAT на этом пути сломал бы ответы.

**Шаг 3. P-CSCF находит I-CSCF.** P-CSCF не знает S-CSCF абонента. Он спрашивает у
`lab-dns` SRV-запись `_sip._udp.<IMS_DOMAIN>`, получает адрес `lab-icscf:5060` и
пересылает ему `REGISTER`.

**Шаг 4. I-CSCF выбирает S-CSCF.** I-CSCF отправляет в HSS Diameter-запрос UAR:
«кто обслуживает этого абонента?». PyHSS отвечает именем S-CSCF из профиля
абонента, и I-CSCF пересылает `REGISTER` в `lab-scscf:6060`.

**Шаг 5. Аутентификация и профиль.** S-CSCF запрашивает у HSS вектор аутентификации
(MAR). PyHSS вычисляет его по IMS-ключам K/OPc из своей базы `lab-mysql`. S-CSCF
отвечает телефону `401 Unauthorized` с challenge; телефон считает ответ по ключам
своей ISIM и повторяет `REGISTER`. S-CSCF сверяет ответ, загружает из HSS профиль с
правилами iFC (SAR) и отвечает `200 OK`. Регистрация хранится в S-CSCF, ключи — в HSS.

**Шаг 6. Ответы возвращаются к телефону.** `401` и `200` идут обратно той же цепочкой
CSCF. P-CSCF отправляет их на `12.1.1.5`: маршрут `12.1.1.0/24 via 192.168.70.134`
приводит пакет в UPF, тот заворачивает его в туннель к телефону. Если этого
маршрута или правила на UPF нет, телефон бесконечно повторяет `REGISTER`.

**Шаг 7. INVITE и привязка медиа.** Пользователь набирает 1003. `INVITE` с SDP
(адрес и порт, куда телефон ждёт звук) приходит на P-CSCF. P-CSCF по протоколу NG
просит `lab-rtpengine` выделить порт и заменяет в SDP адрес телефона на
`192.168.70.161:<порт из 30000–30100>`. Ответ собеседника он обрабатывает так же.
С этого момента обе стороны шлют звук только в RTPengine.

**Шаг 8. S-CSCF вызывает SIP AS по iFC.** S-CSCF проверяет правила iFC абонента. Для
исходящего `INVITE` правило отправляет вызов на `as.<IMS_DOMAIN>:5070`, то есть в
`lab-sip-as` (интерфейс ISC). Правило задаёт `DefaultHandling 0`: если AS недоступен,
обычный вызов всё равно проходит.

**Шаг 9. SIP AS выбирает услугу.** SIP AS сравнивает номер назначения с номерами
услуг из `lab.env`. 1003 — перевод. AS сам отвечает `200 OK` от имени услуги, чтобы
вызов дальше не шёл. Затем он по HTTP передаёт Call-ID в Media Adapter
(`/sessions`, порт 8091) и открывает сессию в Voice Agent (`/calls`, порт 8093) с
адресом RTPengine, куда отправлять звук. Если медиа в SDP не привязано к RTPengine
(телефон обошёл наш P-CSCF), AS отвечает `488` и в журнал пишет
`AS rejected unanchored media`.

**Шаг 10. Звук в AI.** Голос телефона идёт по RTP через UPF в RTPengine. Media
Adapter работает в сетевом пространстве RTPengine: видит те же пакеты и по NG
узнаёт, какие порты относятся к какому Call-ID. Для номеров AI звук уже в
PCMU/8000: если телефон говорит AMR/AMR-WB, RTPengine перекодирует его на шаге 7.
Media Adapter окнами по 100 мс отправляет PCMU в AI Worker (`POST /observe`, порт
8092). В AI попадает только звук абонента, без SIP-идентификаторов.

**Шаг 11. Распознавание и перевод.** AI Worker собирает окна в реплику: ждёт паузы
700 мс или 5 с непрерывной речи. Реплика попадает в очередь, свободный обработчик
распознаёт её Whisper и переводит. В режиме `baseline` перевод делает Qwen через
`lab-llm-worker` во внутренней сети `lab-ai-backend`, в CPU-режимах — OPUS-MT прямо в
AI Worker.

**Шаг 12. Ответ голосом.** AI Worker передаёт текст перевода в Voice Agent
(`/calls/<id>/reply`). Voice Agent синтезирует английскую речь Piper, кодирует в
PCMU и отправляет RTP с порта 41000 в RTPengine. RTPengine пересылает звук на
`12.1.1.5` через UPF, и телефон слышит перевод.

**Завершение.** Пользователь кладёт трубку: `BYE` проходит P-CSCF и S-CSCF до SIP AS.
AS по HTTP закрывает сессии в Media Adapter и Voice Agent, AI Worker дообрабатывает
последнюю реплику и очищает состояние вызова. RTPengine освобождает порты.

Другие вызовы отличаются только шагами 9–12. При обычном вызове 1001 → 1002 SIP AS
не отвечает сам, а возвращает `INVITE` в S-CSCF, и тот доставляет вызов второму
телефону. Media Adapter наблюдает звук, но обычный разговор не зависит от AI: если
остановить AI Worker, RTP продолжает идти. Вызов на 1004 (запись) после уведомления
сохраняет реплики и расшифровку в `local/private/recordings`. Пара 1005/1006
(двусторонний перевод) — два отдельных вызова к услуге: каждый участник слышит
только перевод речи другого.

Тестовые клиенты `lab-sipue1/2` начинают сразу с шага 2: они стоят в сети ядра, без
5G-сессии, и регистрируются паролем (SIP Digest), а не ключами SIM. Все шаги с 3 по
12 они проходят так же, как телефон.

## 4. Что меняется в ядре OAI

Наши скрипты не трогают ядро. Владелец ядра один раз меняет четыре вещи.

DNN `ims` с собственным пулом адресов нужен, чтобы телефон получил IMS-адрес и
адреса IMS-серверов. Пул задаётся в `dnns` конфигурации SMF и должен совпадать с
`IMS_UE_CIDR`; DNN также добавляется в `smf_info`/`upf_info` нужного S-NSSAI и в
подписку абонента в UDR. Если телефоны ходят и в IMS, и в интернет через один пул,
укажите его в обоих параметрах: `IMS_UE_CIDR` и `INTERNET_UE_CIDR`.

Адреса DNS и P-CSCF передаёт SMF: `smf.ue_dns` — наш `DNS_IP`, `smf.ims.pcscf_ipv4` —
наш `PCSCF_IP`. В OAI `ue_dns` общий для всех DNN, поэтому интернет-запросы телефона
тоже пойдут в наш DNS; он пересылает чужие имена на `DNS_UPSTREAM_*`.

NAT на UPF выключается для IMS (`enable_snat: no`). Причина в том, что адрес телефона
записан внутри SIP и SDP: если UPF подменит адрес источника, P-CSCF и RTPengine
будут отвечать не туда. Для интернета NAT нужен, поэтому его возвращает одно правило
`iptables`: `MASQUERADE` для пула UE, кроме адресов сети ядра (`! -d LAB_NETWORK_CIDR`).
Правило теряется при пересоздании контейнера UPF, поэтому добавьте его в entrypoint UPF.

Обратный путь к телефону обеспечиваем мы: init-скрипты P-CSCF, S-CSCF, RTPengine и
DNS добавляют маршрут `IMS_UE_CIDR via UPF_IP`. От ядра нужно только, чтобы UPF
принимал такие пакеты из своей сети N6 — для OAI в одной Docker-сети это так.

## 5. Что делает `start.py`

`python3 scripts/start.py --check` читает `lab.env` и проверяет: IMS-домен выведен из
MCC/MNC (Kamailio и PyHSS сами строят realm из них), все адреса уникальны и лежат в
`LAB_NETWORK_CIDR`, UPF в той же сети, пулы UE вне неё, Compose-конфигурация валидна.
Затем смотрит в реальную сеть ядра: такая сеть есть, подсеть совпадает, наши адреса
не заняты чужими контейнерами. Контейнеры он не запускает.

Без `--check` скрипт собирает и поднимает контейнеры (`--ims-only` — только DNS,
MySQL, PyHSS, CSCF, RTPengine). Затем ждёт REST API PyHSS и заводит четырёх абонентов
([provision.py](../scripts/provision.py)). Если I-CSCF и S-CSCF ещё не установили
Cx-соединение с HSS (Compose мог поднять их раньше PyHSS), скрипт ждёт Cx-слушателя
PyHSS, перезапускает CSCF и ждёт соединения. Если Cx уже открыт, CSCF не трогаются:
повторный запуск (как в туториале 2) не сбрасывает регистрации телефонов. Работающие
контейнеры с неизменной конфигурацией Compose тоже не пересоздаёт. В полном запуске
скрипт дополнительно ждёт `healthy` у AI Worker (прогрев Whisper и LLM). `STARTED`
значит, что сервисы готовы; вызовы проверяют тесты из `app/tests/integration`.

Тестовые клиенты `lab-sipue1/2` скрипт не запускает: они в профиле Compose `test`, их
поднимает каждый тест и удаляет при завершении.

Provisioning не перезаписывает ключи существующего абонента. Если ключи в `lab.env`
разошлись с HSS, запуск останавливается с подсказкой; замена — явно:
`python3 scripts/provision.py --apply --replace-keys`. SQN при этом сохраняется.

## 6. Проверка по шагам вызова

Проверяйте по порядку и не переходите к следующему шагу, пока текущий не прошёл:
каждый шаг опирается на предыдущие. Номера совпадают с [разделом 3](#3-один-вызов-от-начала-до-конца).

**Шаги 1–2: телефон получил IMS-сессию и его пакеты доходят до нас.** Это уровень
ядра. В журнале SMF должна быть сессия DNN `ims` с адресом из `IMS_UE_CIDR`. В
настройках телефона (или `*#*#4636#*#*` на Android) видно, что зарегистрирована
IMS/VoNR-сессия. Дошёл ли `REGISTER` до P-CSCF, покажет журнал:

```bash
docker logs --since 5m lab-pcscf 2>&1 | grep -i register | tail
```

Пустой журнал при включённом телефоне означает, что пакеты не дошли: проверьте DNN
и адрес P-CSCF в SMF и правило NAT на UPF. Если вместо адреса телефона в журнале
адрес UPF, NAT не выключен.

**Шаги 3–5: регистрация в IMS.** Сначала проверьте наши серверы без телефона:

```bash
bash app/tests/integration/verify-ims.sh
```

Тест проверяет DNS-зону, наличие абонентов и Cx в PyHSS, маршрут к пулу UE через UPF
и регистрирует двух тестовых клиентов. Если он не прошёл, телефон тоже не
зарегистрируется; строка `FAIL:` укажет компонент. Если тест прошёл, а телефон нет,
причина в данных абонента: смотрите `docker logs --tail 200 lab-scscf`. Повторяющиеся
`401` без `200` означают, что ключи K/OPc в `lab.env` (и в HSS) не совпадают с SIM.
`403`/`404` от I-CSCF — абонента с таким IMSI нет в HSS или неверен IMS-домен.

**Шаг 6: ответы доходят до телефона.** Если P-CSCF принимает `REGISTER`, а телефон
повторяет его снова и снова, ответы не возвращаются. Проверьте маршрут и путь до UPF:

```bash
docker exec lab-pcscf ip route get 12.1.1.5
```

Ответ должен содержать `via <UPF_IP>`. Маршрут есть, ответа нет — UPF не принимает
пакеты к пулу из сети ядра.

**Шаг 7: обычный вызов и медиа.** Позвоните с 1001 на 1002. Если вызов соединяется,
но звука нет или он в одну сторону, смотрите `docker logs lab-rtpengine`: в сессии
должны быть адреса обоих телефонов. Звук от RTPengine к телефону идёт тем же
маршрутом через UPF, что и SIP (шаг 6).

**Шаги 8–12** (iFC, SIP AS и AI) проверяются после запуска AI — в
[туториале 2](guide-2-ims-ai.md#5-проверка-по-шагам-812). Все проверки используют один
стенд: запускайте их по одной и не во время чужих звонков.

## 7. Диагностика

Начинайте с уровня, на котором оборвался вызов ([раздел 2](#2-три-уровня-одного-вызова)).
Если нет IP-сессии или пакеты не доходят, дело в ядре и сети, и менять IMS бесполезно.
Если пакеты есть, но нет `200 OK`, ищите в IMS и ключах. Если вызов установлен, но
нет звука или перевода, проблема в медиа и AI. Смена модели AI не исправит ошибку
ядра или SIP.

**Запуск не проходит.** `start.py --check` пишет, что сеть ядра не найдена: ядро не
запущено или `CORE_NETWORK_NAME` не совпадает с `docker network ls`. Сообщение
о подсети значит, что `LAB_NETWORK_CIDR` отличается от `docker network inspect`.
Сообщение «уже занят контейнером» — наш адрес совпал с адресом контейнера ядра;
выберите другой свободный адрес в `lab.env`. Ошибка `port is already allocated`
означает, что на хосте занят опубликованный порт REST PyHSS (`PYHSS_API_PORT`).

**Контейнеры работают, регистрации нет.** Убедитесь, что `verify-ims.sh` проходит.
Если `FAIL` на Cx (`I_Open`/`R_Open`), CSCF стартовали раньше HSS — повторите
`start.py`, он перезапустит их в правильном порядке. Если не проходит DNS, смотрите
`docker logs lab-dns`. Ключи телефона проверяйте по журналу S-CSCF (раздел 6, шаги 3–5).
Не сбрасывайте SQN и не отключайте аутентификацию, чтобы обойти ошибку.

**Телефон зарегистрирован, вызов не проходит.** Если телефон отправляет `INVITE` с
`100rel`/`precondition` как обязательными, SIP AS отклоняет его: PRACK/UPDATE не
реализованы. Если AS пишет `AS rejected unanchored media`, медиа не привязано к
RTPengine — телефон ходит в IMS не через наш P-CSCF.

**Вызов есть, звука нет.** Сравните адреса в `docker logs lab-rtpengine` с адресами
телефонов и проверьте маршрут к пулу UE (раздел 6, шаг 6). Звук в одну сторону почти
всегда означает, что не работает обратный путь через UPF или NAT включён.

**Звук есть, AI молчит.** Это уже уровень AI — диагностика в
[туториале 2](guide-2-ims-ai.md#8-диагностика-ai).

**Контейнер перезапускается.** `docker inspect --format '{{.State.OOMKilled}}' <контейнер>`
и `docker stats --no-stream` покажут нехватку памяти; лимиты — `*_MEMORY_LIMIT` в `lab.env`.
