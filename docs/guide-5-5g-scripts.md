# Туториал 5. Проверка через 5G скриптами

Тот же прогон, что в [туториале 4](guide-4-5g-manual.md), одной командой: gNB и два UE
OAI в RF Simulator, PJSUA внутри namespace UE, вызовы через 5G в IMS и AI. Как
устроены радио, абоненты и клиент, разобрано в части 1 туториала 4; здесь — только
запуск, что делает каждый скрипт и где смотреть журналы. Стенд запущен по туториалам
[1](guide-1-ims-core.md)–[3](guide-3-sip.md), нужен собранный OAI RAN на том же хосте
и `sudo`; запускать от обычного пользователя.

# Часть 1. Команды

**1. Прогон целиком**

```bash
scripts/verify-5g.sh
```

Результат через 4–5 минут:

```text
gNB: NGSetupResponse получен
UE1: 10.46.0.3
UE2: 10.46.0.4
===== 5G: PDU-сессии UE =====
PASS: UE1: туннель oaitun_ue1 (10.46.0.3) — scripts/rfsim.sh up
...
===== A: UE1 -> переводчик 1003 =====
PASS: Voice Agent: перевод озвучен полностью
PASS: UE1: получил приветствие и перевод (RX 372 > 241)
===== B: UE2 -> UE1 (1002 -> 1001) =====
PASS: UE1: звук от собеседника (RX 1100 > 500)
PASS: UE2: звук от собеседника (RX 1100 > 500)
===== C: UE2 -> расшифровка 1004 =====
PASS: AI Worker: фраза UE2 распознана
===== D: UE1 -> UE2: перевод ru-en и запись =====
PASS: SIP AS: запись обеих ног после уведомления
PASS: Voice Agent: перевод UE1 озвучен английским голосом
PASS: AI Worker: запись закрыта
===== E: UE2 -> *UE1: разовый перевод =====
PASS: SIP AS: перевод en-ru
===== F: SIP AS остановлен: UE1 -> UE2 =====
PASS: UE1: 200/INVITE без SIP AS (DefaultHandling)
5G UE -> IMS -> AI: PASS
rfsim остановлен
```

Это то же, что `scripts/rfsim.sh up && bash app/tests/integration/verify-5g-ue.sh;
scripts/rfsim.sh down`: радио останавливается и тогда, когда тест упал.

**2. По частям**

Радио можно держать поднятым и гонять тест несколько раз:

```bash
scripts/rfsim.sh up
scripts/rfsim.sh status
bash app/tests/integration/verify-5g-ue.sh
scripts/rfsim.sh down
```

`status` показывает процессы gNB/UE и адреса туннелей.

**3. Другие пути и конфигурации**

Значения по умолчанию — как на стенде партнёра. Свои задаются в `lab.env` или в
окружении:

| Переменная | По умолчанию |
|---|---|
| `OAI_RAN_DIR` | `~/openairinterface5g` |
| `OAI_RAN_CONF_DIR` | `~/projects/oai_configs` |
| `RFSIM_GNB_CONF` | `band78_20mhz.conf` |
| `RFSIM_UE_CONFS` | `ue0.conf ue1.conf` |

**4. Бенчмарк задержек**

```bash
python3 scripts/bench_5g.py --rounds 3
```

Сам поднимает и останавливает радио, если оно не запущено. Измеряет на одних часах
хоста:

- путь: маршрут UE к P-CSCF идёт в `oaitun_ue1`, счётчики туннеля растут на каждый ping;
- RTT ping до P-CSCF через 5G и напрямую с хоста; разница — цена 5G-тракта (в rfsim
  она зависит от загрузки CPU и не равна задержке настоящего радио);
- SIP: REGISTER с Digest (от первого запроса до `200`, включая `401`), INVITE UE1 → UE2
  до `180`/`200`, INVITE в переводчик;
- переводчик: от последнего голосового пакета, пришедшего в AI Worker, до первого
  голосового RTP ответа из Voice Agent, и этапы — фраза целиком (речь и пауза конца фразы),
  очередь, STT, перевод, синтез. Оценка «в трубке» добавляет RTT 5G.

Отчёт печатается и сохраняется в `local/bench/5g-latency-<время>.json`.

**5. Профилирование CPU и задержек перевода**

```bash
scripts/profile.sh            # 5 раундов фразы, полный перебор настроек AI
scripts/profile.sh --quick    # меньше вариантов перебора, простой 15 с вместо 30
scripts/profile.sh --rounds 3 --no-sweep    # только сценарии; --no-scenarios — только перебор
```

Стенд IMS + AI должен быть запущен. Скрипт сам останавливает и поднимает rfsim по
сценариям и в конце возвращает его в прежнее состояние; тестовые клиенты и временные
контейнеры удаляются и при сбое, и при Ctrl-C. Полный прогон — порядка часа (дольше
всего перебор `small` на одном потоке). Последние строки:

```text
==================== ИТОГ PROFILE ====================
#   RES   ШАГ        РЕШАЮЩАЯ СТРОКА / ПРИЧИНА
1   PASS  preflight  PREFLIGHT: PASS
2   PASS  S1         SCENARIO S1: DONE (0 раундов, 0 отказов)
...
9   SKIP  S5         translate не прошёл verify-services.sh (...)
11  PASS  report     REPORT: .../report.md
PROFILE: PASS — ...
REPORT: local/profile/<UTC>/report.md
```

Как читать отчёт — [часть 4](#часть-4-как-читать-отчёт-профилирования).

# Часть 2. Как устроено

**[rfsim.sh](../scripts/rfsim.sh) `up`** — шаги 1–5 туториала 4:

1. Копии конфигураций в `local/rfsim/`: адрес NG/N3 gNB заменён адресом хоста на мосту
   ядра (шлюз сети `lab-pcscf`), DNN UE — `IMS_DNN`, модели канала рядом.
2. gNB в фоне; ожидание `Received NGSetupResponse` до 30 с.
3. Параметры UE (частота, numerology, SSB) — из строки, которую печатает gNB.
4. Namespace `ue1`/`ue2` через `multi-ue.sh`, если их ещё нет.
5. UE по очереди: следующий стартует только после адреса у предыдущего, ожидание до
   двух минут на каждый.

Процессы идут в фоне с `</dev/null`, чтобы не забирать терминал. Если адреса не
дождались, скрипт завершается с ошибкой и оставляет радио работать для разбора.

**`rfsim.sh down`** — шаг 9: сначала UE по `SIGINT`, пока gNB ещё работает (UE успевают
отключиться от сети), затем gNB, через 10 с — `SIGKILL` оставшимся. Останавливаются
только процессы с копиями из `local/rfsim/`: чужой gNB на том же хосте не трогается.
Если до запуска уже работает любой softmodem, `up` отказывается стартовать.

**[verify-5g-ue.sh](../app/tests/integration/verify-5g-ue.sh)** — шаги 6–8 и тесты A–F:

- PDU-сессии: туннель у каждого UE, адрес в `IMS_UE_CIDR`, маршрут `LAB_NETWORK_CIDR` в
  туннель, ping P-CSCF;
- корень PJSUA в `local/rfsim/pjsua-root` (распаковывается один раз) и фраза с 20 с
  тишины;
- клиенты в фоне; команды консоли — через FIFO `/tmp/control-ueN` в корне вместо
  клавиатуры;
- регистрация: `REGISTER 200` и контакт `IMSI@адрес туннеля` в ответе S-CSCF;
- тест A: приветствие, `llm_reply state=sent` до 120 с, RX больше пакетов приветствия;
- тест B: UE2 → UE1, оба вызова `CONFIRMED`, через 20 с RX больше 500 у обоих, BYE дошёл;
- тест C: `utterance_processed` с ненулевым `transcript_chars`;
- тест D: UE1 → UE2 — `languages=ru-en`, `record started ... legs=2`, английский перевод
  в ноге B, `recording_finalized` после BYE;
- тест E: UE2 → `*UE1` — `languages=en-ru`;
- тест F: `lab-sip-as` остановлен — UE1 → UE2 всё равно получает 200/INVITE.

Номера плеера и вызова для `cc`/`cd` скрипт читает из `cl`, RX — из `dq`. В конце
клиенты получают `ha` и `q`, остатки снимаются `pkill` по `chroot`.

**Журналы**

| Файл | Что в нём |
|---|---|
| `local/rfsim/gnb.log` | gNB: NG Setup, PDU Session Setup |
| `local/rfsim/ue1.log`, `ue2.log` | UE: регистрация, PDU-сессия, туннель |
| `local/rfsim/pjsua-ue1.log`, `pjsua-ue2.log` | PJSUA: SIP, `cl`, `dq` |

# Часть 3. Диагностика

**`UE1 без PDU-сессии`**

```bash
grep -E 'Registration Accept|PduSession|Establishment Accept|REJ|TUN Interface' local/rfsim/ue1.log
```

- есть `TUN Interface ... configured` — сессия есть, адрес не увидел скрипт; проверьте
  `sudo ip netns exec ue1 ip -o addr`;
- есть `ESTABLISHMENT_REJ` — сеть отказала: `docker logs --tail 2000 oai-smf`
  (`--since` у SMF ненадёжен, часы журнала могут не совпадать с часами хоста);
- после `PduSessionEstablishRequest` ничего — `grep -i pdusession local/rfsim/gnb.log`.

После разбора — `scripts/rfsim.sh down`.

**`gNB не подключился к AMF`** — `grep -E 'SCTP|errno|bind' local/rfsim/gnb.log`; если
порт занят, где-то работает другой gNB.

**`softmodem уже запущен`** — остался прошлый прогон (`scripts/rfsim.sh down`) или
работает чужой gNB: его не трогайте, договоритесь о времени.

**Терминал печатает «лесенкой»** после прерванного прогона — `stty sane`.

**Тест A медленный или `interrupted`.** Рядом с rfsim Qwen на CPU в 2–3 раза
медленнее; у `llm_reply` запас 120 с. `state=interrupted` означает, что ответ перебили:
фраза должна звучать один раз, проверьте `cc`/`cd` в `pjsua-ue1.log`.

Каталог `local/rfsim/` после прогонов можно удалить целиком:
`sudo rm -rf local/rfsim` (в `pjsua-root` есть файлы устройств от root).

# Часть 4. Как читать отчёт профилирования

`scripts/profile.sh` пишет всё в `local/profile/<UTC>/`: `report.md` (читать),
`report.json` (то же для скриптов), `profile.log` (журнал прогона), `scenarios/S?.json`
и `sweep-idle.json`/`sweep-rfsim.json` (сырые замеры), `sweep/` (фразы и план перебора).

**Сценарии.** S1 — простой стенд; S2 — rfsim без звонков; S3 — SIPUE1 из сети ядра
звонит на переводчик `VOICE_TRANSLATOR_MSISDN`; S4 — то же с UE1 через 5G (как
`bench_5g.py`); S5 — одновременно переводимый звонок UE1 → UE2 через translate B2BUA и
SIPUE1 на переводчик. S2/S4/S5 — SKIP, если нет rfsim или `sudo`; S5 — ещё и если
последний `verify-all` записал FAIL/SKIP для `verify-services` или звонок UE1 → UE2
не установился. Фраза одна: «Добрый день. Как у вас дела?» голосом тестовых клиентов.

**CPU по сценариям** — занятые ядра (1.0 = одно ядро целиком), среднее / p95 по
отсчётам раз в 0,5 с. `host` — весь хост из `/proc/stat` (предел — `nproc`), контейнеры
стенда и ядра OAI — их cgroup, `rfsim-gnb` и `rfsim-ue` — процессы `nr-softmodem` и
`nr-uesoftmodem` (оба UE вместе). Сравнивайте S1 с S2 (цена rfsim) и S3 с S4 (звонок
под нагрузкой rfsim). Если p95 `lab-ai-worker` близко к его лимиту `AI_WORKER_CPU_LIMIT`
(в `report.json` — `cpu.limits`), AI упирается в лимит контейнера, а не в хост.

**Задержка по этапам** — медиана (мин–макс) по раундам: ожидание паузы (VAD) от
последнего голосового пакета до готовой фразы (≈ `AI_UTTERANCE_SILENCE_MS`), очередь,
распознавание, перевод, синтез и итог «конец речи → первый голосовой RTP ответа». Сумма
этапов меньше итога на доставку RTP и опрос Media Adapter.

**Перебор настроек AI** — без звонка, в одноразовом контейнере из образа работающего
`lab-ai-worker` с его лимитами CPU и памяти и его томами моделей (только чтение, без
сети): модель Whisper (`tiny`, `base`, `small` — какие есть в кэше; нет — строка с
причиной), потоки `AI_STT_CPU_THREADS` 1/2/4/8 (не больше `nproc`; больше лимита CPU
контейнера не ускоряют), STT и перевод — код сервиса. «Качество» — `1 − WER` по словам
после нормализации регистра и пунктуации против текста фраз (`SIP_UE_TEST_UTTERANCE` и
русские реплики `interpreter-dialogue-v2.json`); числа словами и цифрами считаются
разными словами, поэтому смотрите разницу с эталоном, а не абсолютное значение. «CPU,
мс» — процессорное время на фразу (все потоки). Строка «поток. 1» — потоковый режим
`AI_STREAMING_ENABLED=1`: время от начала речи до первого устойчивого частичного
результата (верхняя оценка: снимки по `AI_STREAM_INTERVAL_MS` идут подряд).

**Итог.** Узкое место — самый долгий этап в звонке под нагрузкой (S4, без rfsim — S3),
плюс узлы CPU у предела. Оценка варианта = пауза (700/500/300 мс, считается
арифметически) + STT и перевод из перебора + синтез и очередь из того же сценария.
Вариант укладывается, если оценка ≤ 2000 мс и качество не хуже эталона `compact`
(`base`, потоки STT из `ai-profiles.json`) больше чем на 10 п.п. В таблице — до трёх
таких вариантов по возрастанию CPU, для каждой пары «модель, потоки» — с самой длинной
укладывающейся паузой. Если подходящих нет, отчёт пишет это прямо. Перебор при rfsim
важнее перебора при простое: без rfsim отчёт оценивает простой и пишет об этом.
