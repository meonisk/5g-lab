# 7. Полный гайд: 5G, IMS, услуги, тест UE ↔ UE и настоящий телефон

Стенд в этом виде закончен: услуги работают, путь через 5G проверен, замеры — в
[документе 6](6-status.md). Этот документ объясняет, как всё устроено целиком, как
поднять тест «телефон ↔ телефон» через эмулятор радио и что нужно сделать, чтобы
подключить настоящий телефон.

Установка стенда — [документ 1](1-install.md), сервисы и номера —
[документ 2](2-architecture.md), замеры — [документ 3](3-5g-and-profiling.md).

## 1. Общая картина

```text
 Телефон ──радио──> gNB ──N2 (NGAP)──> AMF ── AUSF/UDM/UDR (ключи SIM)
                     │                  │
                     │                 SMF ──N4 (PFCP)──> UPF
                     └──N3 (GTP-U)───────────────────────> UPF ──N6──> сеть IMS
                                                                        │
          P-CSCF ─> I-CSCF ─> S-CSCF ── HSS (PyHSS, Diameter Cx)        │
            │                   │                                        │
            │                   └─ISC─> сервер услуг lab-sip-as          │
            │                                                            │
          RTPengine (весь звук) ─> Media Adapter ─> AI Worker ─> Voice Agent
```

Три слоя, каждый можно понять отдельно:

| Слой | Чьё | Что делает |
|---|---|---|
| Ядро 5G (OAI CN5G) | ваше, стенд только настраивает | пускает телефон в сеть, выдаёт адрес, пересылает его пакеты |
| IMS | стенд | регистрирует телефон как абонента связи, соединяет звонки, вызывает услуги |
| Услуги и AI | стенд | перевод, запись, расшифровка; распознавание, перевод и синтез речи на CPU |

## 2. Как работает ядро 5G

### Компоненты

| Компонент | Роль |
|---|---|
| gNB | базовая станция: радио с телефоном с одной стороны, ядро с другой |
| AMF | вход в ядро: принимает регистрацию телефона (NAS), ведёт его состояние |
| AUSF, UDM, UDR | проверка SIM: UDR хранит ключи K/OPc и разрешённые сети данных (DNN), UDM считает векторы 5G-AKA, AUSF проверяет ответ |
| SMF | открывает мобильную сессию (PDU-сессию): выдаёт адрес, DNS, адрес P-CSCF, выбирает UPF |
| UPF | пересылает пакеты телефона: GTP-туннель со стороны gNB (N3), обычный IP со стороны сети (N6) |
| NRF | справочник, через который компоненты ядра находят друг друга |

### Подключение телефона

1. **Регистрация.** Телефон по радио отправляет в AMF запрос регистрации с
   идентификатором SIM. AMF через AUSF и UDM получает вектор 5G-AKA, телефон отвечает,
   ответ сходится — телефон в сети. SIM при этом проверяет и сеть: ключи на SIM и в UDR
   должны совпадать.
2. **PDU-сессия в сеть `ims`.** Телефон просит сессию на DNN `ims`. SMF проверяет, что
   этот DNN разрешён абоненту в UDR, выдаёт адрес из пула `IMS_UE_CIDR`
   (`10.0.9.0/24`), адрес DNS и адрес P-CSCF (в PCO — служебных опциях сессии), и по
   PFCP настраивает UPF.
3. **Пакеты.** Всё, что телефон отправляет в эту сессию, gNB заворачивает в GTP-U и
   отправляет в UPF; UPF разворачивает и отправляет в Docker-сеть ядра, где стоят
   контейнеры IMS. Обратно — так же: у каждого контейнера IMS есть маршрут
   `IMS_UE_CIDR via UPF_IP`.

### Что стенд меняет в ядре (`scripts/core-setup.sh apply`)

| Изменение | Почему |
|---|---|
| UPF без NAT для сети `ims` | адрес телефона записан внутри SIP; подменённый адрес ломает ответы и звук |
| NAT только для интернета | телефон по-прежнему выходит в интернет |
| SMF отдаёт `PCSCF_IP` и `DNS_IP` | телефон сам узнаёт, куда регистрироваться и как разрешать имена IMS |
| демонстрационный IMS OAI выключен | чтобы телефоны не попадали в него |

## 3. Как работает IMS

### Компоненты

| Компонент | Контейнер | Роль |
|---|---|---|
| P-CSCF | `lab-pcscf` | первый SIP-сервер телефона; привязывает звук звонка к RTPengine |
| I-CSCF | `lab-icscf` | спрашивает у HSS, какой S-CSCF обслуживает абонента |
| S-CSCF | `lab-scscf` | проверяет ключи, хранит регистрацию, по iFC вызывает серверы услуг |
| HSS | `lab-pyhss` + `lab-mysql` | абоненты IMS: ключи, номера, профиль услуг (iFC) |
| RTPengine | `lab-rtpengine` | через него идёт весь звук; перекодирует AMR телефона в PCMU для услуг |
| DNS | `lab-dns` | имена `*.ims.mnc001.mcc001.3gppnetwork.org` |

### Регистрация в IMS

1. Телефон отправляет `REGISTER` на P-CSCF (адрес из PDU-сессии).
2. P-CSCF → I-CSCF. I-CSCF спрашивает HSS (Diameter UAR), какой S-CSCF назначить, и
   передаёт запрос туда.
3. S-CSCF берёт у HSS вектор аутентификации (MAR) и отвечает `401` с вызовом.
4. Телефон считает ответ на SIM и повторяет `REGISTER` с ответом. S-CSCF проверяет,
   сохраняет регистрацию и загружает профиль абонента с правилами iFC (SAR).
5. `200 OK` — телефон в IMS и может звонить.

По 3GPP вызов и ответ считаются по IMS-AKA (ключ SIM), а SIP между телефоном и
P-CSCF защищён IPsec. Как это сделано на стенде — раздел 6.

### Звонок

1. Телефон отправляет `INVITE` с SDP (какие кодеки, куда слать звук).
2. P-CSCF заменяет адрес звука в SDP на адрес RTPengine: весь звук звонка проходит
   через RTPengine.
3. S-CSCF звонящего проходит его правила iFC по приоритету и по очереди отправляет
   звонок на серверы услуг (ISC). Каждый сервер услуг возвращает звонок в S-CSCF.
4. После услуг звонящего S-CSCF находит вызываемого (через I-CSCF и HSS), проходит его
   входящие правила iFC и отправляет звонок на его P-CSCF и телефон.
5. Ответ `200 OK` идёт обратно тем же путём, звук — через RTPengine.

## 4. Наша реализация услуг

### Где что живёт

| Часть | Где | Что делает |
|---|---|---|
| профили абонентов | `lab.env` (`UE1_SERVICES`, `UE1_LANGUAGE`, …) | какие услуги и какой язык у абонента |
| запись в HSS | `scripts/provision.py` | строит iFC из профиля и записывает в PyHSS |
| сервер услуг | `app/services/sip-as/` | один контейнер, модуль услуги выбирается по адресу в `Route` |
| перевод между абонентами | `ims_sip/services/translate.py` | B2BUA: нога A звонящий ↔ стенд, нога B стенд ↔ вызываемый |
| запись | `ims_sip/services/record.py` | уведомление каждой стороне, затем запись обеих сторон |
| номера 1003–1006 | `ims_sip/services/numbers.py` | звонок заканчивается на Voice Agent |
| звук в AI | `app/services/media-adapter/` | делит сетевое пространство с RTPengine, берёт копию RTP звонка, шлёт в AI Worker кусками по 100 мс |
| распознавание и перевод | `app/services/ai-worker/` | делит речь на фразы, Whisper, OPUS-MT, запись разговора |
| озвучка | `app/services/voice-agent/` | Piper синтезирует перевод, RTP уходит в звонок через RTPengine |

Порядок услуг (приоритеты iFC), отказ сервера услуг и запись — в
[документе 2](2-architecture.md#как-звонок-попадает-в-услуги).

### Звонок UE1 → UE2 с переводом и записью

У UE1 (русский) в профиле `translate,record`, у UE2 (английский) услуг нет.

1. UE1 звонит на 1002. S-CSCF по iFC приоритета 10 отправляет `INVITE` на
   `translate.as`.
2. translate AS видит: языки разные, у звонящего есть услуга. Он отвечает UE1 сам
   (нога A) и создаёт новый звонок к UE2 (нога B). Нога B снова идёт через S-CSCF и
   остальные правила iFC — так в цепочку попадает record AS.
3. record AS помечает звонок для записи; каждая сторона слышит уведомление на своём
   языке.
4. Звук обеих ног идёт через RTPengine. Media Adapter отправляет каждую ногу в AI
   Worker отдельно.
5. AI Worker закрывает фразу на паузе (600 мс, или 250 мс после 2,5 с речи),
   распознаёт её, переводит на язык другой стороны.
6. Voice Agent синтезирует перевод и отправляет его в ногу собеседника. Каждый слышит
   другого только в переводе.
7. `BYE` с любой стороны закрывает обе ноги, запись закрывается файлом
   `completed.json`.

Если перевести нельзя (одинаковые языки, телефон не принял PCMU, AI не отвечает),
translate AS пропускает звонок дальше без перевода — разговор не обрывается.

## 5. Тест UE ↔ UE через 5G (эмулятор радио)

### Что эмулируется

| Настоящее | В тесте |
|---|---|
| эфир между телефоном и базовой станцией | OAI RF Simulator: отсчёты радиосигнала передаются по сокету |
| базовая станция | OAI `nr-softmodem` — настоящий стек gNB |
| модем телефона | OAI `nr-uesoftmodem` — настоящий стек 5G NR UE с SIM из конфигурации |
| звонилка телефона | PJSUA внутри сетевого пространства UE |
| ядро, IMS, услуги | настоящие, те же, что для телефона |

### Что нужно

- Собранный OAI RAN: `~/openairinterface5g` (`OAI_RAN_DIR`), бинарники в
  `cmake_targets/ran_build/build/`.
- Конфигурации: `~/projects/oai_configs` (`OAI_RAN_CONF_DIR`) — gNB `band78_20mhz.conf`
  (`RFSIM_GNB_CONF`), UE `ue0.conf` и `ue1.conf` (`RFSIM_UE_CONFS`). В конфигурациях UE
  — IMSI, K, OPc тех же абонентов, что `UE1_*` и `UE2_*` в `lab.env` и в UDR ядра.
- `sudo` (OAI, сетевые пространства, `chroot`).
- Запущенные ядро и стенд (`python3 scripts/start.py`).

### Как поднимается радио (`scripts/rfsim.sh up`)

1. Копирует конфигурации в `local/rfsim/`: gNB получает адрес хоста на мосту ядра для
   NG и N3, UE — DNN `IMS_DNN`. Исходные файлы не меняются.
2. Запускает gNB и ждёт `NGSetupResponse` от AMF.
3. Для каждого UE создаёт сетевое пространство `ue1`/`ue2` (OAI `multi-ue.sh`) и
   запускает в нём UE. UE подключаются по очереди: регистрация и PDU-сессия занимают до
   двух минут, одновременный вход под нагрузкой срывается.
4. Ждёт туннель `oaitun_ue1` с адресом из пула IMS — это PDU-сессия в сеть `ims`.

`RFSIM_CPUSET` привязывает gNB и UE к своим ядрам, `AI_WORKER_CPUSET` — AI Worker к
своим ([документ 3](3-5g-and-profiling.md#привязка-к-ядрам-при-rfsim)).

```bash
scripts/rfsim.sh up        # gNB и два UE
scripts/rfsim.sh status    # процессы и адреса туннелей
scripts/rfsim.sh down      # остановить
```

### Как звонят эмулированные телефоны

Docker не запускает контейнер в чужом сетевом пространстве, поэтому PJSUA запускается
через `chroot` в корень образа `lab-pjsua` (`local/rfsim/pjsua-root`) внутри
пространства UE. Его пакеты идут: туннель UE → gNB → UPF → IMS. Команды консоли PJSUA
передаются через FIFO. Код — `scripts/lib/ue5g.py` и
`app/tests/integration/verify-5g-ue.sh`.

### Проверки

```bash
scripts/verify-5g.sh                                # 4–5 минут, сам поднимает и гасит радио
python3 scripts/profile/conversation.py --5g        # длинный разговор UE1 ↔ UE2, ~3 минуты
```

`verify-5g.sh` проверяет: PDU-сессию в пуле IMS, регистрацию с адресом из туннеля, 1003
для UE1, обычный звонок UE2 → UE1 со звуком в обе стороны, расшифровку 1004, перевод и
запись UE1 → UE2, `*номер`, звонок при остановленном сервере услуг. Итог —
`5G UE -> IMS -> AI: PASS`.

`conversation.py --5g` — UE1 и UE2 одновременно говорят 96 с разговора, отчёт по
фразам, задержке и точности ([документ 3](3-5g-and-profiling.md#длинный-разговор-в-обычном-темпе)).

Журналы: `local/rfsim/gnb.log`, `ue1.log`, `ue2.log` (радио и ядро),
`pjsua-ue*.log`, `bench-ue*.log` (SIP), `docker logs lab-scscf`, `lab-sip-as`.

### Если не работает

| Симптом | Что делать |
|---|---|
| `gNB не подключился к AMF` | ядро не запущено или занят адрес NG: `grep -E 'SCTP\|errno' local/rfsim/gnb.log` |
| `UE без PDU-сессии` | ключи UE не совпадают с UDR, нет DNN `ims` у абонента или rfsim не хватает процессора: `grep -E 'PduSession\|reject' local/rfsim/ue1.log`, `docker logs --tail 20 oai-smf` |
| `softmodem уже запущен` | остался прошлый запуск: `scripts/rfsim.sh down` |
| регистрация в IMS не проходит | `docker exec lab-pcscf ip route get <адрес UE>` должен идти `via <UPF_IP>`; на UPF не должно быть NAT (`scripts/core-setup.sh check`) |
| терминал печатает «лесенкой» | `stty sane` |

## 6. Настоящий телефон

### Чем телефон отличается от эмулятора

| | Эмулятор (сейчас) | Настоящий телефон |
|---|---|---|
| радио | RF Simulator | SDR (например, USRP B210) с антеннами; gNB тот же |
| SIM | ключи в конфигурации UE | программируемая SIM с USIM и ISIM |
| вход в IMS | SIP Digest, пароль — ключ K | IMS-AKA по ключу SIM |
| защита SIP | нет | IPsec между телефоном и P-CSCF |
| кодек | PCMU | AMR-WB (обязателен для VoNR), часто EVS |
| QoS голоса | общий поток сессии | телефон и сеть могут требовать выделенный поток 5QI=1 |

### Что понадобится

- **Телефон** с 5G SA и VoNR, который поддерживает диапазон из конфигурации gNB
  (сейчас n78). Многие телефоны включают VoNR/VoLTE только для известных операторов:
  для тестовой сети MCC 001 / MNC 01 может понадобиться инженерное меню или настройки
  оператора в телефоне.
- **Программируемая SIM** (например, sysmoISIM) и программатор (pySim): IMSI, K, OPc,
  MCC/MNC, приложение ISIM (IMPI, IMPU, домен IMS). Без ISIM телефон выводит имена IMS
  из IMSI — стенд это понимает.
- **SDR** с антеннами и gNB OAI, собранный с его драйвером; конфигурация gNB — та же,
  что для rfsim, но с параметрами SDR вместо `--rfsim`.

### Шаги

1. **SIM.** Записать IMSI, K, OPc для `UE1` (или `UE2`). MCC/MNC — `001`/`01`, как в
   `lab.env` и ядре.
2. **Ядро.** Абонент в UDR с теми же IMSI/K/OPc и разрешёнными DNN `ims` и `internet`.
   `scripts/core-setup.sh check` — ядро настроено под IMS.
3. **Стенд.** Те же ключи в `lab.env` (`UE1_IMSI`, `UE1_IMS_K`, `UE1_IMS_OPC`), номер,
   язык и услуги абонента. Затем `python3 scripts/start.py` — ключи и iFC попадут в
   HSS. Ключи уже были другими — `python3 scripts/provision.py --apply --replace-keys`.
4. **Радио.** Запустить gNB с SDR (PLMN 001/01, TAC и срез как в AMF). Эмулятор rfsim
   при этом остановлен: `scripts/rfsim.sh down`.
5. **Телефон.** Сеть — только 5G (SA), точка доступа `ims` с типом `ims` (если телефон
   не создал её сам), включить VoNR. Телефон регистрируется в сети, открывает сессию
   `ims`, получает адрес P-CSCF и регистрируется в IMS сам.
6. **Проверить регистрацию:** в `docker logs lab-scscf` — регистрация IMPU абонента с
   адресом из `10.0.9.0/24`.
7. **Позвонить:** 1003 (переводчик), 1004 (запись), второму телефону или тестовому
   клиенту. Номера — [документ 2](2-architecture.md#номера-и-услуги).

### Что на стенде есть, но с телефоном не проверено

| Что | Состояние | Что сделать при подключении |
|---|---|---|
| IMS-AKA | S-CSCF и PyHSS поддерживают AKAv1-MD5 по тем же K/OPc; проверен только Digest | при `401` по кругу — сверить ключи и OPc; счётчик SQN не сбрасывать |
| IPsec с P-CSCF | P-CSCF собран с поддержкой IPsec (`WITH_IPSEC`, права `NET_ADMIN`) | смотреть `docker logs lab-pcscf` на `sec-agree`; если телефон без IPsec не регистрируется — разбирать настройки IPsec P-CSCF |
| AMR-WB → PCMU | P-CSCF просит RTPengine добавить PCMU (`codec-transcode-PCMU`), услуги AI принимают только PCMU | проверить, что RTPengine умеет кодек телефона: `docker exec lab-rtpengine rtpengine --codecs`; без PCMU перевод между абонентами пропускается (звонок идёт без него), номера 1003–1006 отвечают `488` |
| `100rel`, `precondition` | услуги AI не обслуживают звонки, которые их требуют (`Require:`): перевод пропускается, номера 1003–1006 отвечают `488` | если телефон их требует — услуги AI нужно доработать; обычные звонки между абонентами идут |
| QoS 5QI=1 | Rx/N5 выключен: у PCF ядра нет Diameter | если телефон обрывает звонок без выделенного потока — нужна интеграция P-CSCF с PCF по N5 |
| EVS | не проверен | — |

Частые ошибки при подключении телефона — [документ 1](1-install.md#частые-ошибки).
