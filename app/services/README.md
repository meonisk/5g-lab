# Как читать сервисы

Начните с нужного сценария, а не со всех файлов сразу. Пути ниже — от `app/services/`.
У каждого сервиса короткая точка входа и пакет с его логикой.

## Путь речи

1. `sip-as/ims_sip/routing.py` обрабатывает SIP и выбирает сценарий звонка.
2. `media-adapter/ims_media/` принимает RTP и отправляет аудио AI Worker.
3. `ai-worker/ims_ai/segmentation.py` собирает кадры в реплики по паузам.
4. `ai-worker/ims_ai/queueing.py` передаёт готовую реплику свободному обработчику.
5. `ai-worker/ims_ai/utterances.py` распознаёт речь и измеряет время STT.
6. `transcription.py` нормализует и сохраняет текст; `replies.py` переводит
   или формирует ответ. Оба файла находятся в `ai-worker/ims_ai/`.
7. `voice-agent/ims_voice/media.py` последовательно озвучивает ответы звонка
   и отправляет PCMU обратно через RTPengine.

## Где используются библиотеки

- Flask: маршрутизация HTTP, разбор JSON, стандартные ошибки.
- Waitress: многопоточный HTTP-сервер без отладочного режима.
- HTTPX: межсервисные запросы и обращения к локальной LLM.
- `queue.Queue`, `threading.Condition`, `dataclasses`: задания и координация потоков.
- faster-whisper: локальное распознавание; Ollama: локальная LLM;
  существующий TTS backend выбирается через ENV.

Общие правила HTTP собраны в `lab_common/http.py`. Здесь нет отдельного сервиса:
этот пакет копируется в четыре Docker-образа. Поэтому их контекст сборки —
`app/services/`. Изменили общий пакет — пересоберите все четыре образа.

SIP/SDP и PCMU/RTP остаются небольшими лабораторными реализациями, а не полным
телефонным SDK. Не добавляйте универсальную фабрику или новый framework ради
одного обработчика: сначала используйте обычную функцию и существующую библиотеку.

## Состояние и ограничения

`settings.py` / `runtime.py` отделяют настройки и состояние от обработки.
`voice-agent/ims_voice/calls.py` управляет жизнью звонка: повторное уведомление
не создаёт ещё один проигрыватель. У каждого звонка своя очередь TTS.

Каждый сервис запускается **одним процессом**: звонки, очереди и история находятся
в памяти. `SERVICE_HTTP_THREADS` меняет только число HTTP-потоков;
`AI_PROCESSING_WORKERS` — число обработчиков реплик. Это не распределённая очередь
и не гарантия восстановления после перезапуска. Реплики выделяются по аудиопаузам,
а не по семантическому завершению предложения.

## Изменение и проверка

Из корня репозитория:

```powershell
python -m pip install -r requirements-dev.txt
./scripts/check.ps1
./scripts/compose.ps1 build sip-as media-adapter ai-worker voice-agent
./scripts/compose.ps1 up -d --no-deps sip-as media-adapter ai-worker voice-agent
```

После изменения аудио/маршрутизации выполняйте подходящие live-тесты из
`app/tests/integration/` **по одному**. Unit-тесты не доказывают прохождение RTP.
Пустые строки отделяют этапы обработки. Комментарии поясняют контракт,
причину решения и ограничения, а не повторяют синтаксис. Параметры запуска находятся
в `app/config/lab.env`, секреты и записи — только в игнорируемом `local/`.
